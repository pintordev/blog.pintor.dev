## Summary
- **rebase**: 커밋 기록을 정리해 선형 히스토리를 만든다.
- **merge**: 기존 기록을 보존하고 안전하게 합친다.
- **개인 브랜치에서는 rebase, 공유 브랜치에서는 merge**가 기본 원칙이다.

---

## Background
Git을 사용하다 보면 브랜치를 합치는 상황은 자주 발생한다.  
하지만 막상 **rebase와 merge 중 무엇을 써야 하는지**는 헷갈리기 쉽다.

특히 팀 작업 환경에서는 잘못된 선택이
- 히스토리를 이해하기 어렵게 만들거나
- 다른 팀원의 작업을 꼬이게 만들 수 있다.

이 글에서는 `rebase`와 `merge`의 차이를 정리하고,  
**상황별로 어떤 선택이 적절한지** 기준을 제시한다.

---

## Git Rebase

### 핵심 개념
기존 커밋들을 **다른 기준 브랜치 위로 다시 쌓는 작업**이다.  
커밋의 내용은 유지되지만 **히스토리는 새로 작성된다**.

### 언제 쓰는가
- 개인 작업 브랜치 정리
- PR 생성 전 커밋 정돈
- 최신 `main` 기준으로 작업 브랜치 갱신

### 특징
- 히스토리가 선형으로 깔끔해진다
- 커밋 흐름을 읽기 쉬워진다
- **기존 커밋 해시가 변경된다**
  - 공유 브랜치에서는 위험

---

## Git Merge

### 핵심 개념
두 브랜치의 변경 사항을 **하나의 병합 커밋으로 합친다**.  
히스토리를 재작성하지 않고 **실제 작업 흐름을 그대로 유지**한다.

### 언제 쓰는가
- `main`, `develop` 같은 공유 브랜치
- 협업 중인 기능 브랜치 병합
- 히스토리 신뢰성이 중요한 경우

### 특징
- 기존 커밋이 그대로 유지된다
- 충돌은 한 번에 처리한다
- merge commit이 생성될 수 있다

---

## Key Differences

| 구분 | rebase | merge |
|:--:|:--:|:--:|
| 히스토리 | 정리된 선형 구조 | 실제 작업 흐름 유지 |
| 커밋 해시 | 변경됨 | 유지됨 |
| 충돌 처리 | 커밋 단위로 여러 번 | 한 번에 처리 |
| 협업 영향 | 공유 브랜치에서는 위험 | 안전 |

---

## When to Use Which

### 개인 작업 브랜치
- rebase 사용 가능
- 커밋 정리 목적

### 팀 / 공유 브랜치
- merge 권장
- 안정성과 히스토리 보존 우선

### PR 기준 추천 흐름
- PR 전: rebase로 커밋 정리
- PR 병합: merge 사용

---

## Key Point
> **히스토리를 다시 쓰는 건 혼자일 때만,
> 같이 쓰는 브랜치는 merge로 합친다.**

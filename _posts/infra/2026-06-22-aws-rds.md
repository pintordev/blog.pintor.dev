## Summary

- **AWS RDS**: AWS가 운영 부담을 대신 지는 관리형 관계형 데이터베이스 서비스.
- EC2 직접 설치 대비 핵심 차이: **운영 자동화**, **고가용성**, **보안 패치** — 이 세 가지를 RDS가 대신 처리한다.
- RDS가 적합하지 않은 상황도 분명히 존재한다: 극도의 커스터마이징, 비용 최소화, OS 수준 접근이 필요한 경우.

---

## Background

데이터베이스를 EC2에 직접 설치하는 것은 전통적인 방식이다. 서버에 SSH로 접속해 MySQL이나 PostgreSQL을 설치하고, 설정 파일을 손으로 편집하고, 백업 스크립트를 작성하고, 장애 발생 시 직접 복구한다. 이 모든 과정은 엔지니어의 시간과 전문 지식을 요구한다.

클라우드가 일반화되면서 이런 운영 부담을 클라우드 공급자에게 위임하는 관리형 서비스(Managed Service)가 등장했다. AWS RDS(Relational Database Service)가 대표적이다. 2009년 출시된 RDS는 운영의 복잡성을 숨기고 개발자가 데이터베이스 자체에 집중할 수 있게 한다.

다만 "관리를 위임한다"는 것은 곧 "제어를 포기한다"는 뜻이기도 하다. 이 트레이드오프를 이해하는 것이 RDS 선택의 핵심이다.

---

## RDS의 주요 이점

### 1. 운영 자동화

EC2에 DB를 직접 운영하면 DBA(Database Administrator) 업무가 자동으로 딸려온다.

| 작업 | EC2 직접 운영 | RDS |
|---|---|---|
| OS 보안 패치 | 직접 적용, 재시작 일정 조율 | AWS가 자동 적용 (유지 관리 창 설정 가능) |
| DB 엔진 버전 업그레이드 | 직접 수행, 테스트 필요 | 콘솔에서 버전 선택, 무중단 또는 단기 중단 업그레이드 |
| 자동 백업 | cron + mysqldump 스크립트 직접 작성 | 자동 스냅샷, 보존 기간 설정 |
| 모니터링 | CloudWatch 에이전트 설치, 설정 | Enhanced Monitoring 기본 내장 |
| 스토리지 용량 초과 | 직접 디스크 증설 | Storage Auto Scaling으로 자동 확장 |

EC2 방식은 이 모든 것을 엔지니어가 직접 처리해야 한다. 팀 규모가 작거나 DBA 전문가가 없는 조직에서는 이 비용이 상당하다.

---

### 2. 고가용성 (Multi-AZ)

프로덕션 DB에서 장애는 서비스 중단으로 직결된다.

**EC2 직접 운영의 한계:**

```
[단일 EC2 인스턴스]
     ↓
  MySQL
     ↓
  장애 발생 → 서비스 다운
  (수동으로 failover 처리)
```

**RDS Multi-AZ:**

```
[가용 영역 A]         [가용 영역 B]
Primary RDS  ←── 동기 복제 ──→  Standby RDS
     ↓                               ↓
  장애 발생          자동 failover (약 60~120초)
                    → DNS 엔드포인트가 Standby로 전환
```

RDS Multi-AZ는 다른 가용 영역에 스탠바이 인스턴스를 유지하며 동기 복제한다. Primary에 장애가 발생하면 DNS 엔드포인트가 자동으로 Standby로 전환된다. 애플리케이션 코드 변경 없이 failover가 처리된다.

EC2에서 이와 동등한 수준의 HA를 구축하려면 MySQL Replication + Keepalived + VIP 또는 Pacemaker 같은 별도 구성이 필요하다.

---

### 3. 읽기 분산 (Read Replica)

트래픽이 증가하면 DB가 병목이 된다. 쓰기는 Primary에 집중하고, 읽기를 복제본으로 분산하는 패턴이 일반적이다.

RDS는 Read Replica를 콘솔 클릭 몇 번으로 생성한다. 비동기 복제로 Primary의 데이터를 Replica에 전파하며, 최대 5개(MySQL/PostgreSQL)까지 생성 가능하다. 리전 간 Read Replica도 지원한다.

```
애플리케이션
    ↓
Writer Endpoint → Primary RDS (쓰기)
Reader Endpoint → Read Replica 1 (읽기)
                → Read Replica 2 (읽기)
                → Read Replica 3 (읽기)
```

EC2에서 이를 구현하려면 복제 설정, GTID 관리, 지연(lag) 모니터링까지 직접 구성해야 한다.

---

### 4. 보안 내장

RDS는 보안 구성의 기본값이 이미 강화되어 있다.

- **저장 데이터 암호화**: AES-256 기반 암호화를 활성화 옵션 하나로 적용
- **전송 중 암호화**: SSL/TLS 연결 강제 가능
- **VPC 격리**: 퍼블릭 인터넷에 노출되지 않는 Private Subnet 배치
- **IAM 인증**: DB 비밀번호 없이 IAM 역할로 인증 가능
- **자동 보안 패치**: CVE 발견 시 AWS가 패치 적용

EC2 직접 운영에서는 이 모든 설정을 엔지니어가 누락 없이 직접 적용해야 한다.

---

### 5. 스냅샷과 Point-in-Time Recovery

RDS는 자동 백업을 활성화하면 5분 간격으로 트랜잭션 로그를 S3에 저장한다. 이를 통해 보존 기간 내 임의의 시점으로 DB를 복원할 수 있다.

```
백업 보존 기간: 7일 설정 시

"어제 오후 2시 37분 상태로 복원해줘"
→ RDS 콘솔에서 날짜/시간 입력
→ 새 RDS 인스턴스로 복원 완료
```

EC2에서는 mysqldump나 xtrabackup으로 주기적 백업을 직접 구성하고, 복원 절차도 직접 작성해야 한다.

## EC2 직접 설치 vs RDS 비교 요약

| 항목 | EC2 직접 설치 | RDS |
|---|---|---|
| 초기 설정 비용 | 낮음 (설치만 하면 됨) | 낮음 (콘솔에서 몇 분) |
| 운영 비용 (인력) | 높음 | 낮음 |
| OS 접근 | 가능 (SSH) | 불가 |
| DB 설정 유연성 | 완전한 자유 | 파라미터 그룹 범위 내 |
| 고가용성 구성 | 직접 구성 필요 | Multi-AZ 옵션으로 즉시 |
| 백업/복구 | 직접 구현 | 자동화, PITR 지원 |
| 요금 | EC2 + 스토리지 | RDS 인스턴스 요금 (EC2 대비 약 20~30% 추가) |
| 지원 엔진 | 제한 없음 | MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Aurora |

---

## RDS가 적합하지 않은 상황

RDS가 만능은 아니다. 다음 상황에서는 EC2 직접 운영이 더 나은 선택일 수 있다.

### 1. OS 수준 접근이 필요한 경우

RDS는 기저 OS와 파일시스템에 대한 접근을 허용하지 않는다.

- 특정 OS 파라미터 튜닝 (`vm.swappiness`, `huge_pages` 등)
- `xtrabackup`을 이용한 물리 백업 직접 실행
- 커스텀 플러그인이나 UDF(User Defined Function) 설치
- 파일시스템 직접 접근이 필요한 `LOAD DATA INFILE` 운영

이런 요구사항이 있다면 EC2가 불가피하다.

---

### 2. 비용 최소화가 최우선인 경우

RDS는 EC2 단독 운영에 비해 비용이 높다. 동일 사양의 EC2 인스턴스 대비 약 20~30% 추가 비용이 발생한다.

대용량 트래픽과 대형 인스턴스를 장기 운영하는 환경에서 이 비용 차이는 상당하다. 비용 절감이 최우선이고 운영 인력이 충분하다면 EC2 직접 운영이 합리적일 수 있다.

---

### 3. RDS가 지원하지 않는 DB 엔진이 필요한 경우

RDS가 지원하는 엔진은 정해져 있다. 다음이 필요한 경우는 EC2를 써야 한다.

- CockroachDB, TiDB 같은 분산 NewSQL
- ScyllaDB
- 특정 마이너 버전 고정 (RDS는 지원 버전 범위가 제한됨)
- 커뮤니티 특수 빌드

---

### 4. 규정 준수상 관리형 서비스를 사용할 수 없는 경우

일부 금융·의료 규제 환경에서는 클라우드 공급자가 인프라에 접근할 수 있는 관리형 서비스 자체를 제한하는 경우가 있다. 이 경우 EC2에 직접 설치해 완전한 제어권을 유지해야 한다.

---

### 5. 특수한 스토리지 구성이 필요한 경우

- NVMe SSD를 직접 마운트해 I/O 레이턴시를 극한으로 낮춰야 하는 경우
- 로컬 스토리지 기반 클러스터 구성 (Percona XtraDB Cluster 등)
- 스토리지 엔진 수준의 커스터마이징

---

## Key Point

> **RDS의 본질은 "운영의 복잡성을 돈으로 사는 것"이다. 자동 백업, Multi-AZ 고가용성, 보안 패치, 모니터링 — 이것들을 직접 구축하고 유지하는 엔지니어링 비용이 RDS 추가 요금보다 크다면 RDS가 합리적이다. 반대로 OS 접근, 특수 엔진, 극단적인 비용 최적화가 필요하다면 EC2 직접 운영이 맞다. "RDS가 좋다/나쁘다"가 아니라 팀의 운영 역량과 요구사항에 따라 선택해야 한다.**

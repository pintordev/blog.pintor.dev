## 문제

> 링크: [프로그래머스 42884](https://school.programmers.co.kr/learn/courses/30/lessons/42884)

차량들의 진입/진출 지점이 주어질 때, 모든 차량이 최소 한 번은 카메라를 만나도록 하는 데 필요한 최소 카메라 개수를 구하는 문제다.

## 접근

### 그리디 - 구간 스케줄링(진출 지점 기준 정렬)

각 차량의 이동 구간을 진출 지점 기준으로 오름차순 정렬한다. 순회하면서 지금까지 설치한 카메라를 만나지 못하는 구간이 나오면, 그 구간의 진출 지점에 새 카메라를 설치한다. 진출 지점은 해당 구간에서 가장 늦은 지점이라 이후 구간들과 겹칠 가능성을 최대화하는 선택이 되고, 이를 통해 최소 개수로 모든 구간을 커버할 수 있다.

진입 지점 기준으로 정렬하면 반례가 존재해 정당성이 깨지므로, 반드시 진출 지점 기준으로 정렬해야 한다.

## 풀이

```java
import java.util.Arrays;

public int solution(int[][] routes) {
    Arrays.sort(routes, (a, b) -> Integer.compare(a[1], b[1]));
    int cnt = 0;
    int pos = Integer.MIN_VALUE;
    for (int[] route : routes) {
        if (route[0] <= pos) continue;
        pos = route[1];
        cnt++;
    }
    return cnt;
}
```

## 회고

처음에는 `Arrays.sort(routes, Comparator.comparingInt(r -> r[1]))`로 정렬했는데, 채점에서 간헐적으로 효율성 테스트 하나가 시간초과로 떨어졌다. 알고리즘은 `O(n log n)`이고 차량 수도 최대 10,000대라 시간초과가 날 이유가 없어 보였는데, 원인은 정렬 로직이 아니라 비교자를 만드는 방식에 있었다.

`Comparator.comparingInt`의 실제 구현은 다음과 같다.

```java
public static <T> Comparator<T> comparingInt(ToIntFunction<? super T> keyExtractor) {
    Objects.requireNonNull(keyExtractor);
    return (Comparator<T> & Serializable)
        (c1, c2) -> Integer.compare(keyExtractor.applyAsInt(c1), keyExtractor.applyAsInt(c2));
}
```

`comparingInt(r -> r[1])` 한 줄이 실제로는 람다 2개를 만든다. 키 추출 람다 `r -> r[1]`, 그리고 `comparingInt` 내부의 비교 람다인데, 이 비교 람다는 `Comparator<T> & Serializable` 교차 타입으로 캐스팅되어 있어 일반 람다보다 무거운 `altMetafactory` 부트스트랩 경로를 탄다. 이 부트스트랩은 콜사이트별 1회성 비용이라 보통은 무시할 수준이지만, 이 문제처럼 알고리즘 실행 시간 자체가 마이크로초 단위인 짧은 프로그램에서는 전체 측정 시간을 지배할 수 있다.

`(a, b) -> Integer.compare(a[1], b[1])`로 비교자를 직접 작성하면 람다 1개, 일반 부트스트랩 경로만 타서 오버헤드가 줄고, 실제로 이후 제출에서 안정적으로 통과했다. 정렬 비교자를 유틸리티 메서드로 짤지 직접 람다로 짤지가 실행 시간에 실질적인 차이를 만들 수 있다는 걸 확인했다.

## Summary

- JVM은 클래스 로더(Class Loader) → 런타임 데이터 영역(Runtime Data Area) → 실행 엔진(Execution Engine) 세 축으로 나뉜다 — 클래스를 "가져오고 검증하고", "메모리에 저장하고", "실행하는" 파이프라인이다
- 바이트코드는 기계어가 아니다 — CPU가 직접 실행하는 기계어와 달리, 바이트코드는 JVM만 이해하는 플랫폼 독립적 중간 표현이다. 자바는 소스를 바이트코드로 컴파일(`javac`)한 뒤 그 바이트코드를 실행 시점에 JVM이 다시 해석/컴파일하는 **2단계 하이브리드**라, "컴파일 언어냐 인터프리터 언어냐"는 질문에는 둘 다라고 답하는 게 정확하다
- 클래스 로딩은 로딩 → 링킹(검증·준비·분석) → 초기화 순서로 진행되며, 부모 위임 모델(Parent Delegation Model) 덕분에 사용자가 `java.lang.String`을 직접 정의해도 core 클래스가 대체되지 않는다
- 런타임 데이터 영역 중 Method Area와 Heap은 모든 스레드가 공유하고, PC Register·Stack·Native Method Stack은 스레드마다 독립적으로 생성된다 — 이 구분이 StackOverflowError와 OutOfMemoryError가 서로 다른 원인에서 발생하는 이유다
- 실행 엔진은 처음엔 인터프리터로 바이트코드를 한 줄씩 해석하다가, 반복적으로 실행되는(hot) 코드만 JIT 컴파일러가 네이티브 코드로 컴파일해 캐싱한다 — 인라이닝·이스케이프 분석 같은 투기적(speculative) 최적화가 틀렸다고 판명되면 역최적화(Deoptimization)로 다시 인터프리터로 되돌아간다
- GC나 일부 JIT 작업은 모든 스레드가 안전하게 멈춘 지점(Safepoint)에서만 수행할 수 있다 — 객체 그래프가 일관되지 않은 중간 상태에서 멈추면 마킹·재배치가 깨지기 때문이다
- Java 8에서 PermGen이 사라지고 Metaspace로 대체된 건 "클래스 메타데이터를 고정 크기 힙 영역에 가두지 않고 네이티브 메모리를 쓰겠다"는 결정이다 — 잦았던 `OutOfMemoryError: PermGen space`의 구조적 해결책
- GC가 회수하는 건 "도달 불가능한" 객체뿐이다 — `static` 컬렉션에 계속 add만 하거나 `ThreadLocal`을 정리하지 않는 등 **의도치 않게 도달 가능 상태를 유지**하면, GC가 정상 동작해도 자바에서 메모리 누수가 발생한다

## JVM이란 무엇인가

`javac`는 소스 코드를 기계어가 아니라 **바이트코드**라는 중간 표현으로 컴파일한다. 바이트코드는 특정 OS나 CPU 아키텍처에 종속되지 않는 명세이므로, 이를 해석·실행하는 JVM만 각 플랫폼에 맞게 구현되어 있으면 "Write Once, Run Anywhere"가 성립한다. 이 구조 덕분에 Java뿐 아니라 Kotlin·Scala·Groovy처럼 바이트코드 명세만 지키는 어떤 언어든 같은 JVM 위에서 함께 실행되고 상호 호출도 가능하다 — JVM은 사실 "자바 전용 실행기"가 아니라 "바이트코드 실행기"에 가깝다.

**바이트코드 vs 기계어**

둘 다 사람이 직접 읽기 어려운 저수준 명령어라는 점은 같지만 본질이 다르다. **기계어(Machine Code)** 는 특정 CPU 아키텍처(x86, ARM 등)가 직접 실행할 수 있는 이진 명령어로, 그 CPU에서만 동작한다. **바이트코드(Bytecode)** 는 어떤 CPU에도 종속되지 않는 JVM 전용 중간 표현이라 그 자체로는 하드웨어가 실행할 수 없고, 반드시 JVM(인터프리터 또는 JIT 컴파일러)을 거쳐 실제 기계어로 변환된 뒤에야 실행된다. 기계어가 "하드웨어가 이해하는 최종 언어"라면, 바이트코드는 "JVM이라는 소프트웨어가 이해하는 중간 언어"다.

**자바는 컴파일 언어인가, 인터프리터 언어인가?**

엄밀히는 **둘 다에 해당하는 2단계 하이브리드**다. `javac`가 소스 코드를 바이트코드로 바꾸는 과정은 컴파일이고, 그렇게 만들어진 바이트코드를 실행 시점에 JVM이 한 줄씩 해석(인터프리팅)하거나 필요하면 네이티브 코드로 다시 컴파일(JIT)하는 과정은 인터프리팅과 컴파일이 혼합된 방식이다. 소스가 곧바로 기계어로 컴파일되는 C 같은 순수 컴파일 언어나, 소스를 즉시 한 줄씩 해석만 하는 Python 같은 순수 인터프리터 언어와 달리, 자바는 "중간 코드로 먼저 컴파일한 뒤, 그 중간 코드를 실행 시점에 다시 해석/컴파일하는" 방식이라고 설명하는 게 정확하다.

**JVM vs JRE vs JDK**

| | 포함 관계 | 역할 |
|---|---|---|
| JVM | — | 바이트코드를 로딩·실행하는 엔진 자체 |
| JRE | JVM + 표준 라이브러리(`java.lang`, `java.util` 등) | 이미 컴파일된 자바 프로그램을 **실행**하는 데 필요한 최소 구성 |
| JDK | JRE + 컴파일러(`javac`), 디버거, `jar` 등 개발 도구 | 자바 프로그램을 **개발**하는 데 필요한 전체 구성 |

### 전체 구조

```
.java 소스
   ↓ javac
.class 바이트코드
   ↓
┌─────────────────────────────────────────────┐
│                    JVM                       │
│  ┌───────────────┐                           │
│  │ Class Loader   │  로딩 → 링킹 → 초기화        │
│  └───────┬───────┘                           │
│          ↓                                   │
│  ┌───────────────────────────────────────┐  │
│  │      Runtime Data Area                 │  │
│  │  Method Area | Heap | Stack | PC | ... │  │
│  └───────┬───────────────────────────────┘  │
│          ↓                                   │
│  ┌───────────────┐   ┌────────────────┐     │
│  │ Execution      │   │ Garbage        │     │
│  │ Engine (JIT)   │   │ Collector      │     │
│  └───────────────┘   └────────────────┘     │
└─────────────────────────────────────────────┘
```

**왜 이렇게 나뉘는가?** "바이트코드를 어떻게 가져올지"(Class Loader), "가져온 걸 어디에 둘지"(Runtime Data Area), "그걸 어떻게 실행할지"(Execution Engine)는 서로 독립적으로 교체 가능한 관심사다. 실제로 클래스 로더는 커스텀 구현(OSGi, 플러그인 시스템)으로 흔히 대체되고, GC 알고리즘도 실행 엔진과 무관하게 옵션으로 교체된다 — 관심사 분리 덕분에 가능한 유연성이다.

## 클래스 로더 (Class Loader)

### 로딩 과정: 로딩 → 링킹 → 초기화

1. **로딩(Loading)** — `.class` 파일을 읽어 바이너리 데이터를 Method Area에 배치하고, 그 내용을 대표하는 `Class` 객체를 Heap에 생성한다.
2. **링킹(Linking)**
   - **검증(Verify)**: 바이트코드가 JVM 명세를 위반하지 않는지 검사한다(스택 오버플로우 유발 코드, 잘못된 타입 캐스팅 등). 컴파일된 `.class` 파일이라도 조작되거나 손상됐을 수 있으므로 실행 전 마지막 방어선 역할을 한다.
   - **준비(Prepare)**: `static` 필드에 타입별 기본값(0, null, false 등)으로 메모리를 할당한다. 아직 개발자가 작성한 초깃값은 대입되지 않는다.
   - **분석(Resolve)**: 심볼릭 레퍼런스(클래스·메서드·필드를 이름으로 참조하는 상태)를 실제 메모리 주소를 가리키는 다이렉트 레퍼런스로 교체한다.
3. **초기화(Initialization)** — `static` 필드에 실제 초깃값을 대입하고 `static` 블록을 실행한다. 이 시점에 클래스가 처음으로 "능동적으로" 사용된다.

**왜 준비와 초기화를 분리하는가?** 준비 단계에서 기본값으로 먼저 슬롯을 확보해두면, 링킹 중 순환 참조가 있는 클래스들 사이에서도 "필드가 아예 존재하지 않는" 상태를 피할 수 있다. 초기화(실제 값 대입, 정적 블록 실행)는 클래스가 처음 능동적으로 사용되는 시점까지 지연(lazy)시켜, 실제로 쓰이지 않는 클래스의 초기화 비용을 아낀다.

### 클래스 초기화는 언제 트리거되는가 (Active Use)

JVM 명세는 클래스를 **처음 "능동적으로 사용"하는 시점**에만 초기화하도록 규정한다. 대표적인 능동적 사용 시점:

- `new`로 인스턴스를 생성할 때
- `static` 메서드를 호출할 때
- `static` 필드를 읽거나 쓸 때 (단, `static final`이면서 컴파일 타임에 값이 확정되는 **상수**는 클래스 파일에 값 자체가 인라인 복사되어 클래스 로딩을 트리거하지 않는다)
- 리플렉션(`Class.forName(name)`)으로 명시적으로 요청할 때
- 하위 클래스를 초기화할 때 (부모 클래스가 먼저 초기화된다)
- JVM 시작 시 `main` 메서드를 가진 클래스

반대로 단순히 타입을 참조하거나(`Foo f;` 선언만) 상수를 읽는 경우는 클래스를 초기화시키지 않는다. **왜 이 구분이 중요한가?** `static` 블록 안에 무거운 초기화 로직(커넥션 풀 생성 등)이 있다면, 그 비용이 언제 발생하는지를 정확히 예측할 수 있어야 하기 때문이다 — 이는 싱글턴 패턴의 "초기화 지연 홀더(Lazy Holder)" 기법이 동작하는 근거이기도 하다.

### 클래스 로더 계층과 위임 모델

```
Bootstrap Class Loader   (JDK 핵심 클래스: java.lang.*, java.util.* ...)
        ↑
Platform Class Loader    (구 Extension Class Loader — 확장 API)
        ↑
Application Class Loader (classpath의 사용자 클래스)
```

클래스 로딩 요청이 오면 Application → Platform → Bootstrap 순으로 먼저 **부모에게 위임**하고, 부모가 찾지 못했을 때만 자신이 로딩을 시도한다(**Parent Delegation Model**).

**왜 위임 모델이 필요한가?** 만약 사용자가 `java.lang.String`이라는 이름의 클래스를 직접 작성해 classpath에 올렸다고 하자. 위임 모델이 없다면 Application Class Loader가 이 가짜 `String`을 먼저 로딩해버려, JDK 핵심 클래스가 사용자 코드로 대체되는 심각한 보안 문제가 생긴다. 위임 모델 덕분에 `String` 요청은 항상 최상위 Bootstrap까지 올라가 진짜 JDK 클래스를 먼저 찾게 되고, 사용자 정의 `java.lang.String`은 애초에 로딩되지 않는다(`SecurityException`).

같은 클래스라도 **로딩한 클래스 로더가 다르면 JVM은 서로 다른 타입으로 취급**한다 — `instanceof`나 캐스팅이 실패할 수 있다. 이는 하나의 JVM 안에서 같은 이름의 클래스를 격리해 동시에 로드해야 하는 WAS(톰캣의 웹앱별 클래스 로더 격리 등)에서 핵심적으로 활용되는 특성이다.

### 클래스 언로딩은 언제 일어나는가

클래스 자체도 메타데이터로서 GC 대상이 될 수 있지만 조건이 까다롭다. 그 클래스를 로딩한 **클래스 로더 인스턴스 자체가 도달 불가능**해져야 하고, 그러려면 그 클래스 로더가 로딩한 모든 클래스의 `Class` 객체와 인스턴스들도 함께 도달 불가능해야 한다. Bootstrap/Platform/Application 같은 표준 클래스 로더는 JVM이 종료될 때까지 root 자체로 취급되어 사실상 언로딩되지 않는다. 반면 WAS가 배포마다 새로 만드는 커스텀 클래스 로더는, 재배포 후에도 이전 배포의 스레드·캐시·리스너가 옛 클래스 로더를 참조한 채 남아 있으면 회수되지 않는다 — 배포를 반복할수록 Metaspace가 누적돼 고갈되는 전형적인 **클래스 로더 누수**다.

## `java` 실행부터 `main()` 시작까지

`java Foo` 명령을 실행했을 때 실제로 벌어지는 일을 순서대로 정리하면 앞서 다룬 개념들이 하나로 연결된다.

1. JVM 프로세스가 구동되고, 진입점 클래스 `Foo`가 (Bootstrap → Platform → Application 순으로 탐색되는) 클래스 로더 체인을 통해 로딩된다.
2. `Foo` 클래스가 검증 → 준비 → 분석의 **링킹** 단계를 거친다.
3. `Foo`가 **초기화**된다 — `static` 필드에 실제 초깃값이 대입되고 `static` 블록이 실행된다. `main` 메서드를 가진 클래스는 앞서 다룬 "능동적 사용" 조건 중 하나로, JVM 시작 시점에 곧바로 초기화 대상이 된다.
4. JVM이 애플리케이션의 **main 스레드**를 만들고, 그 스레드의 Stack에 `main(String[] args)`에 대한 Stack Frame을 쌓아 실행을 시작한다.
5. `main()` 내부의 바이트코드는 처음엔 인터프리터가 한 줄씩 실행하고, 반복 실행되는 부분은 JIT가 점차 네이티브 코드로 대체해 나간다.
6. `main()`이 반환되거나 예외가 밖으로 전파되어도, **다른 non-daemon 스레드가 하나라도 살아있으면 JVM 프로세스는 종료되지 않는다.** 모든 non-daemon 스레드가 끝나야 비로소 JVM이 종료된다 — 예를 들어 `main()`에서 새 스레드를 non-daemon으로 띄워두면, `main()` 자체는 끝나도 프로그램은 계속 떠 있는 이유다.

## 런타임 데이터 영역 (Runtime Data Area)

| 영역 | 공유 여부 | 저장 내용 |
|---|:---:|---|
| Method Area (Metaspace) | 스레드 공유 | 클래스 메타데이터, `static` 변수, Runtime Constant Pool, 메서드 바이트코드 |
| Heap | 스레드 공유 | `new`로 생성된 객체 인스턴스, 배열 |
| Stack | 스레드별 | 메서드 호출마다 쌓이는 Stack Frame |
| PC Register | 스레드별 | 현재 실행 중인 바이트코드 명령어의 주소 |
| Native Method Stack | 스레드별 | JNI를 통한 네이티브(비자바) 메서드 호출용 스택 |

**왜 Stack은 스레드별로 독립적인가?** 메서드 호출은 지역 변수·매개변수·리턴 주소처럼 그 메서드 실행이 끝나면 의미가 없어지는 "호출 단위 상태"를 다룬다. 이 상태가 스레드마다 별도의 Stack에 격리돼 있기 때문에, 여러 스레드가 같은 메서드를 동시에 호출해도 서로의 지역 변수를 침범하지 않는다 — 별도의 동기화 없이도 지역 변수 자체는 스레드 안전한 이유다. 반대로 Heap과 Method Area는 모든 스레드가 공유하므로, 그 안의 객체 상태를 여러 스레드가 함께 바꾸려면 `synchronized`나 `volatile` 같은 명시적 동기화가 필요하다(가시성·순서 보장은 Java Memory Model이 규정하는 영역으로, 이 노트에서는 다루지 않는다).

### Stack Frame의 내부 구조

메서드가 호출될 때마다 Stack에 쌓이는 Frame 하나는 세 부분으로 이루어진다.

- **Local Variable Array**: 메서드의 매개변수와 지역 변수를 인덱스로 접근하는 슬롯 배열. `long`/`double`은 2슬롯을 차지한다.
- **Operand Stack**: 바이트코드 명령어가 연산을 수행하는 작업 공간. 예를 들어 `a + b`는 `a`와 `b`를 이 스택에 push한 뒤 `iadd` 명령으로 pop-계산-push한다 — JVM은 레지스터 기반이 아니라 **스택 기반** 명령어 집합을 쓴다.
- **Frame Data**: 현재 메서드가 속한 클래스의 Runtime Constant Pool에 대한 참조, 예외 처리 테이블, 메서드 정상 종료 시 되돌아갈 리턴 주소 등.

메서드 호출이 끝나면 해당 Frame은 통째로 Stack에서 pop되므로, 지역 변수의 생명주기가 메서드 호출과 정확히 일치한다.

### Method Area 안의 Runtime Constant Pool

각 클래스 파일은 컴파일 시점에 리터럴 값과 심볼릭 레퍼런스(다른 클래스·메서드·필드 이름)를 모아둔 **상수 풀(Constant Pool)** 을 가지며, 클래스가 로딩되면 이 정보가 클래스별 **Runtime Constant Pool**로 Method Area에 적재된다. 앞서 언급한 링킹의 "분석(Resolve)" 단계가 바로 이 심볼릭 레퍼런스를 실제 주소로 바꾸는 과정이다.

문자열 리터럴(`"hello"`)도 이 상수 풀에 등록되지만, 실제 `String` 객체 자체는 Java 7부터 Heap에 있는 별도의 **String Constant Pool**에 저장되고 Runtime Constant Pool은 그 객체에 대한 참조만 가진다. 즉 "상수 풀에 문자열 값이 박제된다"는 통념과 달리, 클래스별 상수 풀과 문자열 인터닝을 위한 String Pool은 서로 다른 저장소다.

### StackOverflowError vs OutOfMemoryError

두 에러는 각각 다른 메모리 영역이 고갈됐을 때 발생한다.

- **StackOverflowError**: 재귀 호출이 너무 깊어 스레드별 Stack의 한계(`-Xss`)를 넘었을 때. Stack Frame이 계속 쌓이기만 하고 반환되지 않는 상황(잘못된 재귀 종료 조건 등)에서 흔히 발생한다.
- **OutOfMemoryError**: 여러 하위 원인이 있고, 메시지로 어느 영역이 문제인지 구분할 수 있다.
  - `Java heap space` — Heap에 살아있는 객체가 너무 많아 새 객체를 할당할 공간이 없을 때
  - `Metaspace` — 클래스 메타데이터가 너무 많이 로드됐을 때(대표적으로 클래스 로더 누수)
  - `GC overhead limit exceeded` — GC가 힙을 거의 회수하지 못한 채 CPU 시간의 대부분(기본 98%)을 GC에 쓰고 있을 때 — "회수는 계속 시도하지만 의미가 없다"는 신호
  - `Unable to create new native thread` — OS 프로세스가 감당할 수 있는 스레드 수(각 스레드가 자기 몫의 Stack을 요구)를 넘었을 때 — Heap이 아니라 스레드 생성 자체의 실패라는 점에서 다른 OOM들과 성격이 다르다

두 에러 모두 "정해진 메모리 한계를 넘었다"는 공통점이 있지만, Stack은 호출 깊이 문제(로직 결함에 가깝다), Heap/Metaspace는 객체 수명 관리 문제(GC와 직결된다)라는 점에서 접근 방식이 다르다.

두 클래스 모두 `Exception`이 아니라 **`Error`를 상속**한다. `Exception`은 프로그램이 `catch`로 잡아 복구를 시도할 수 있는 예외 상황을 뜻하지만, `Error`는 JVM 자체가 정상적으로 동작하기 어려운 심각한 문제를 나타낸다. 기술적으로는 `catch (Throwable t)`로 잡을 수 있지만, 이미 스택이나 힙이 고갈된 상태라 예외 처리 로직 자체를 실행할 여유 메모리도 없을 수 있어 잡아서 복구하는 대신 애플리케이션을 재시작하는 것이 일반적인 대응이다.

## 실행 엔진 (Execution Engine)

### 인터프리터와 JIT 컴파일러

- **인터프리터(Interpreter)**: 바이트코드를 한 줄씩 읽어 즉시 해석·실행한다. 컴파일 과정이 없어 시작이 빠르지만, 매번 같은 코드를 다시 해석하므로 반복 실행되는 코드에는 비효율적이다.
- **JIT 컴파일러(Just-In-Time Compiler)**: 실행 횟수를 카운팅하다가 임계치를 넘어 "자주 실행되는(hot spot)" 코드로 판단되면, 그 부분만 네이티브 머신 코드로 컴파일해 캐싱한다. 이후에는 인터프리터를 거치지 않고 캐싱된 네이티브 코드를 바로 실행한다. **HotSpot VM**이라는 이름 자체가 이 hot spot 탐지 방식에서 왔다.

**왜 처음부터 전부 컴파일하지 않는가?** 정적 컴파일(AOT)은 시작 전 전체 코드를 컴파일해야 해 시작 시간이 길고, 실행 중 실제 어떤 코드가 자주 쓰이는지 모른 채 모든 코드를 동일하게 최적화해야 한다. 반대로 인터프리터만 쓰면 시작은 빠르지만 반복 실행 성능이 나쁘다. JIT는 "일단 인터프리터로 빠르게 시작하고, 런타임에 실제로 뜨거운 코드만 골라 집중적으로 최적화"함으로써 시작 속도와 실행 속도를 동시에 잡는다 — 프로파일링 기반 최적화(Profile-Guided Optimization)의 일종이다.

HotSpot VM은 목적이 다른 두 JIT 컴파일러를 계층적으로 사용한다(**Tiered Compilation**):

| 컴파일러 | 별칭 | 특징 |
|---|---|---|
| C1 | Client Compiler | 컴파일이 빠르고 최적화는 가볍다 — 빠른 웜업이 목적 |
| C2 | Server Compiler | 컴파일에 시간이 걸리지만 인라이닝·루프 최적화 등 공격적으로 최적화한다 — 장시간 실행되는 서버 애플리케이션에 적합 |

기본적으로 C1으로 빠르게 웜업한 뒤, 더 뜨거워진 코드는 C2로 재컴파일하는 단계적 전략을 쓴다.

### JIT의 대표적 최적화 기법

- **메서드 인라이닝(Inlining)**: 호출 비용(스택 프레임 생성, 인자 전달)이 큰 짧은 메서드를 호출부에 그대로 펼쳐 넣는다. 인라이닝은 그 자체로 이득이기도 하지만, 뒤이은 다른 최적화(불필요한 연산 제거 등)가 더 넓은 범위에서 가능해지는 전제 조건이 된다는 점에서 "최적화의 어머니"로 불린다.
- **이스케이프 분석(Escape Analysis)**: 객체가 생성된 메서드 밖으로 "탈출(escape)"하는지, 즉 다른 스레드나 힙의 다른 객체에서 참조될 수 있는지를 정적으로 분석한다. 탈출하지 않는다고 판단되면:
  - **스칼라 치환(Scalar Replacement)**: 객체를 힙에 통째로 할당하는 대신 필드 각각을 지역 변수(스칼라 값)처럼 Stack에 분해해서 저장한다 — 힙 할당과 이후 GC 대상 자체가 사라진다.
  - **락 제거(Lock Elision)**: 다른 스레드가 접근할 수 없는 객체라면 그 객체에 걸린 `synchronized`는 경합할 상대가 없으므로 락 획득/해제 오버헤드를 통째로 제거한다.
- **OSR (On-Stack Replacement)**: 오래 도는 루프는 메서드가 끝나기도 전에 이미 뜨거워질 수 있다. JIT는 메서드 호출이 끝나길 기다리지 않고, 실행 중인 루프의 현재 상태(Stack Frame)를 그대로 컴파일된 네이티브 코드로 즉시 교체한다.
- **역최적화(Deoptimization)**: 위 최적화들은 "지금까지 관측된 패턴이 앞으로도 유지된다"는 가정 위의 **투기적(speculative) 최적화**다. 예를 들어 특정 타입만 호출되는 걸 보고 다형 호출을 단일 구현으로 고정(monomorphic inline caching)했는데, 나중에 새 클래스가 로딩되어 그 가정이 깨지면(uncommon trap) JVM은 최적화된 네이티브 코드를 버리고 해당 지점부터 다시 인터프리터로 되돌아가 안전하게 실행을 이어간다.

### Safepoint와 Stop-The-World

GC의 마킹·압축뿐 아니라 일부 역최적화, 바이어스드 락 해제 같은 JVM 내부 작업은 **모든 애플리케이션 스레드가 동시에 안전한 지점에서 멈춰야** 정확하게 수행할 수 있다. 이 지점을 **Safepoint**라 부르며, 스레드는 메서드 호출·루프 끝·역참조 지점 등 컴파일러가 미리 심어둔 폴링 지점에서 "정지 요청이 있는지" 주기적으로 확인한다.

**왜 아무 지점에서나 멈추면 안 되는가?** 예를 들어 GC가 객체 그래프를 마킹하는 도중인데, 어떤 스레드가 하필 참조를 재배정하는 명령어 중간에 멈춘다면 마킹이 보는 객체 그래프가 일관되지 않은 상태가 된다. Safepoint는 "이 지점에서는 모든 스레드의 참조 관계가 명확히 정의된 상태"임을 컴파일러가 보장하는 지점이므로, 모든 스레드가 각자의 다음 Safepoint에 도달할 때까지 기다렸다가(Safepoint Sync) 일제히 멈추는 것이 바로 흔히 말하는 **Stop-The-World(STW)**다.

## Java 8: PermGen → Metaspace

Java 7까지는 클래스 메타데이터, `static` 변수, Runtime Constant Pool 등을 **PermGen(Permanent Generation)** 이라는 Heap의 일부 고정 영역에 저장했다. Java 8부터는 이 영역이 사라지고 **Metaspace**로 대체됐다.

| | PermGen (~Java 7) | Metaspace (Java 8~) |
|---|---|---|
| 위치 | Heap 내부 | Native(OS) 메모리 |
| 크기 | `-XX:MaxPermSize`로 고정 | 기본적으로 시스템 메모리 한도까지 동적 확장 (`-XX:MaxMetaspaceSize`로 제한 가능) |
| 흔한 장애 | `OutOfMemoryError: PermGen space` | 여전히 `OutOfMemoryError: Metaspace` 가능하지만 훨씬 드묾 |

**왜 바뀌었는가?** PermGen은 크기가 고정돼 있어, 애플리케이션 서버에서 클래스를 계속 동적으로 로딩·언로딩하는 패턴(WAS의 애플리케이션 재배포, 리플렉션·동적 프록시를 많이 쓰는 프레임워크)에서 클래스 로더가 누수되면 금방 한계에 도달해 `OutOfMemoryError: PermGen space`가 발생했다. Metaspace는 Native 메모리를 사용해 필요에 따라 동적으로 커지므로, 이 문제 자체의 발생 빈도를 구조적으로 낮췄다(여전히 무한한 건 아니라서 앞서 다룬 클래스 로더 누수는 여전히 `OutOfMemoryError: Metaspace`로 나타날 수 있다).

참고로 문자열 상수 풀(String Pool)은 이보다 앞서 **Java 7**부터 PermGen에서 Heap으로 옮겨졌다 — GC가 더 활발히 동작하는 Heap으로 옮김으로써, 더 이상 참조되지 않는 인터닝된 문자열도 회수될 수 있게 하기 위해서였다.

## 자바에서도 메모리 누수가 발생하는 경우

"자바는 GC가 있으니 메모리 누수가 없다"는 것은 절반만 맞다. GC는 **도달 불가능한(unreachable)** 객체만 회수한다 — 프로그램 로직상 더 이상 쓰지 않는 객체라도 어딘가에서 여전히 참조하고 있다면(즉 도달 가능하다면) GC는 절대 회수하지 않는다. 자바의 메모리 누수는 대부분 "의도치 않게 계속 도달 가능 상태를 유지하는" 패턴에서 나온다.

- **`static` 컬렉션에 계속 추가만 하는 캐시**: `static Map<K, V> cache = new HashMap<>();`처럼 `static` 필드는 클래스 로더가 살아있는 한 그 자체로 GC Root와 다름없다. 크기 제한이나 만료 정책 없이 계속 `put`만 하면 힙이 서서히 잠식된다 — `WeakHashMap`이나 만료 정책이 있는 캐시(Caffeine 등)로 해결한다.
- **리스너/콜백 등록 후 해제 누락**: 옵저버 패턴에서 구독만 하고 해제하지 않으면, 리스너를 들고 있는 주체(subject)가 살아있는 한 등록된 콜백 객체도 계속 도달 가능한 상태로 남는다.
- **`ThreadLocal` 미정리**: 스레드 풀 환경에서는 스레드가 종료되지 않고 재사용되므로, `ThreadLocal.remove()`를 호출하지 않으면 그 스레드가 들고 있는 `ThreadLocalMap` 엔트리가 다음 작업이 와도 계속 살아있다 — 요청마다 사용자 정보를 담는 `ThreadLocal`을 정리하지 않으면 이전 요청의 데이터가 누적되거나 새어나가는 문제로 이어진다.
- **닫지 않은 리소스**: 여기서 "누수"는 힙 메모리가 아니라 파일 핸들·커넥션처럼 GC가 아예 관여하지 않는 네이티브 리소스에 대한 것이다. `close()`를 호출하지 않으면 해당 객체가 GC로 회수되기 전까지(혹은 영영) 리소스가 반환되지 않는다 — `try-with-resources`로 명시적 해제를 강제하는 이유다.
- **클래스 로더 누수**: 앞서 다룬 대로, 커스텀 클래스 로더가 로딩한 클래스나 인스턴스를 무언가(오래 사는 스레드, 정적 캐시 등)가 계속 참조하면 클래스 로더 자체가 회수되지 않아 Metaspace가 누적된다.

공통된 교훈은 "GC를 믿는 것"이 아니라 **"객체의 참조 수명을 의도한 대로 짧게 유지하는 것"**이 자바에서도 메모리 관리의 핵심이라는 점이다.

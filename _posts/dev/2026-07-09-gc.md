## Summary

- GC는 레퍼런스 카운팅이 아니라 **GC Root에서부터의 도달 가능성(Reachability)** 을 기준으로 "더 이상 쓰이지 않는" 객체를 판단한다 — 이 방식 덕분에 서로를 참조하는 순환 참조 객체도 root에서 끊겨 있으면 함께 회수된다
- 객체 할당은 스레드마다 Eden 안에 미리 확보한 **TLAB(Thread-Local Allocation Buffer)** 안에서 이뤄진다 — 스레드별로 독립된 공간이라 매 할당마다 동기화 없이 포인터만 증가시키면 된다
- **강한/소프트/약한/팬텀 참조**(Strong/Soft/Weak/Phantom Reference)는 "얼마나 쉽게 회수 대상이 되는가"를 코드에서 직접 제어하는 스펙트럼이다 — 캐시는 SoftReference, `WeakHashMap`처럼 키가 사라지면 함께 사라져야 하는 매핑은 WeakReference, 리소스 정리 후처리는 PhantomReference가 쓰인다
- **약한 세대 가설(Weak Generational Hypothesis)** — "대부분의 객체는 생성된 직후 금방 죽는다"는 경험적 관찰에서 힙을 Young/Old로 나누는 세대별 GC가 나왔다. 자주 죽는 Young 영역만 빠르게 자주 훑는 게, 매번 힙 전체를 훑는 것보다 압도적으로 싸다
- Minor GC(Young 대상)는 짧고 잦으며, Full GC(Old를 포함한 전체 대상)는 드물지만 Stop-The-World 시간이 길다 — GC 튜닝의 핵심은 대부분 "Full GC를 얼마나 늦게, 얼마나 짧게 만들 것인가"로 귀결된다
- G1GC는 힙을 고정된 Young/Old 물리 블록이 아니라 균일한 크기의 Region 여러 개로 쪼개고, "가비지가 가장 많은 Region부터" 우선 회수한다(Garbage-**First**) — 정해진 시간 목표(`-XX:MaxGCPauseMillis`) 안에서 회수량을 조절해 STW 시간을 예측 가능한 범위로 관리한다
- Old 영역에 승격시킬 공간이 부족하면 **Promotion Failure**(G1에서는 Evacuation Failure/to-space exhausted)가 발생해, 원래 짧아야 할 Minor GC가 예기치 못한 Full GC로 격상된다 — Old 영역 부족은 튜닝에서 가장 흔히 놓치는 원인이다
- ZGC·Shenandoah 같은 최신 GC는 마킹·압축 같은 무거운 단계까지 애플리케이션 스레드와 동시에(concurrent) 수행해, 힙 크기와 무관하게 STW를 수 ms 이내로 묶는다 — "얼마나 빨리 회수하는가"보다 "회수 중 애플리케이션을 얼마나 오래 멈추는가"가 최신 GC들의 핵심 경쟁 지점이다

## GC란 무엇인가 — 도달 가능성(Reachability)

GC는 힙에 있는 객체 중 **더 이상 참조되지 않는(unreachable) 객체**를 자동으로 찾아 회수한다. 판단 기준은 **GC Root**라 불리는 출발점들에서 참조를 따라갔을 때 도달할 수 있는지 여부다.

**GC Root의 예시**
- 각 스레드 Stack의 지역 변수·매개변수
- Method Area의 `static` 변수
- 활성 스레드(Thread) 자체
- JNI를 통해 네이티브 코드가 들고 있는 참조

```
GC Root (Stack의 지역변수 obj)
   │
   ▼
 Object A ──▶ Object B
                 │
                 ▼
              Object C   ← A, B를 거쳐 도달 가능 → reachable

Object X ──▶ Object Y ──▶ Object X   (서로만 참조, 순환)
   ↑
   어디에서도 이 순환에 들어오는 GC Root 참조가 없음 → 둘 다 unreachable
```

**기본 알고리즘: Mark and Sweep**
1. **Mark**: GC Root에서 시작해 참조를 재귀적으로 따라가며 도달 가능한 모든 객체에 표시한다.
2. **Sweep**: 표시되지 않은(도달 불가능한) 객체를 회수한다.
3. **Compact**(선택적): Sweep으로 힙 곳곳에 생긴 빈 공간(단편화, fragmentation)을 한쪽으로 밀어 정리해, 이후 객체 할당을 빠르게 만든다(포인터 하나만 증가시키면 되는 bump-a-pointer 할당).

**왜 레퍼런스 카운팅을 쓰지 않는가?** 레퍼런스 카운팅은 각 객체가 "나를 참조하는 수"를 직접 들고 있다가 0이 되면 즉시 회수하는 방식이다. 구현은 단순하지만, 위 다이어그램의 X↔Y처럼 두 객체가 서로만 참조하는 **순환 참조**가 생기면 각자의 카운트가 절대 0이 되지 않아 영원히 회수되지 않는다(대표적으로 Python의 참조 카운팅이 이 문제 때문에 별도의 순환 참조 탐지기를 함께 쓴다). GC Root 기반의 도달 가능성 분석은 카운트가 아니라 "루트에서 실제로 닿을 수 있는가"만 보므로, 이런 순환 참조 객체도 자연스럽게 unreachable로 판정돼 회수된다.

**`System.gc()`를 호출하면 바로 GC가 도는가?** 아니다. `System.gc()`는 JVM에게 "지금 Full GC를 한번 고려해 달라"는 **힌트**를 보낼 뿐, 즉시 실행을 강제하지 않는다(`-XX:+DisableExplicitGC`로 이 힌트 자체를 아예 무시하게 만들 수도 있다). 실무에서 코드에 `System.gc()`를 직접 넣는 걸 지양하는 이유이기도 하다 — 언제 실행될지 보장되지 않는데 예측 불가능한 STW만 유발할 수 있다.

## 참조의 강도 — Strong / Soft / Weak / Phantom Reference

기본적인 `Object obj = new Object();` 같은 참조는 모두 **Strong Reference**다. GC는 Strong Reference가 하나라도 살아있으면 절대 회수하지 않는다. 하지만 "메모리가 부족할 때만", "다른 곳에서 안 쓰면 바로", "회수된 뒤 정리 작업이 필요할 때"처럼 회수 시점을 세밀하게 제어하고 싶을 때 `java.lang.ref` 패키지의 참조 타입을 쓴다.

| 종류 | 회수 시점 | 대표 용도 |
|---|---|---|
| Strong | 참조가 남아있는 한 절대 회수되지 않음 | 일반적인 모든 객체 참조 |
| Soft (`SoftReference`) | Strong 참조가 없어져도 바로 회수되지 않고, **메모리가 부족해질 때**(OOM 직전) 회수 | 메모리 여유에 따라 크기가 유동적인 캐시 |
| Weak (`WeakReference`) | Strong 참조가 없으면 **다음 GC 사이클에서 즉시** 회수 | `WeakHashMap`, 캐시 키, 리스너 참조로 인한 누수 방지 |
| Phantom (`PhantomReference`) | 객체가 이미 finalize되어 회수 직전 상태 — `get()`은 항상 `null`을 반환하며, `ReferenceQueue`로 "회수됐다"는 사실만 통지받을 수 있음 | `finalize()`를 대체하는 안전한 리소스 정리(`java.lang.ref.Cleaner`) |

`Object.finalize()`는 원래 리소스 정리 훅으로 쓰였지만, 호출 시점을 예측할 수 없고(GC가 알아서 판단) 실행 도중 예외가 나도 무시되며 성능에도 악영향을 줘 **Java 9부터 deprecated**됐다. `PhantomReference` + `ReferenceQueue` 조합은 "객체가 회수됐다"는 사실을 정확한 타이밍에, 예외 처리도 가능한 형태로 통지받을 수 있어 `finalize()`의 이런 문제들을 구조적으로 피한다 — `Cleaner`가 내부적으로 이 조합을 감싸 더 쓰기 쉽게 만든 API다.

**왜 이런 스펙트럼이 필요한가?** Strong Reference만 있다면, 캐시처럼 "웬만하면 들고 있고 싶지만 메모리가 부족하면 포기해도 되는" 데이터를 표현할 방법이 없다 — 개발자가 직접 크기 제한이나 만료 정책을 관리해야 하고, 자칫하면 JVM 노트에서 다룬 `static` 캐시형 메모리 누수로 이어진다. `SoftReference`는 "메모리가 실제로 부족해지기 전까지는 최대한 살려두라"는 힌트를 GC에게 직접 전달하는 수단이다.

**`WeakReference`와 `ThreadLocal` 누수의 실제 구조**: `ThreadLocalMap`의 각 엔트리는 키(`ThreadLocal` 인스턴스)를 `WeakReference`로 감싸지만, **값(value)은 Strong Reference로 그대로 들고 있다.** `ThreadLocal` 인스턴스에 대한 다른 Strong 참조가 사라지면 다음 GC 때 키는 회수되지만, 엔트리 자체와 값은 `ThreadLocalMap`에 그대로 남는다 — 이 엔트리는 이후 그 스레드가 `get()`/`set()`/`remove()`를 호출해 맵을 정리하는 시점에야 청소된다. 스레드 풀처럼 스레드가 장기간 재사용되는 환경에서 이 정리 시점이 오지 않으면, 키를 잃은 값들이 계속 쌓인다 — 키를 Weak로 만든 것만으로는 완전히 안전하지 않은 이유이며, `ThreadLocal.remove()`를 명시적으로 호출해야 하는 근거다.

## 객체 할당과 TLAB (Thread-Local Allocation Buffer)

Eden에 새 객체를 할당하는 가장 단순한 방법은 "다음 빈 주소를 가리키는 포인터를 하나 두고, 할당할 때마다 그 포인터를 객체 크기만큼 증가시키는" **bump-a-pointer** 방식이다. 문제는 멀티스레드 환경에서 이 포인터를 여러 스레드가 동시에 건드리면, 매 할당마다 CAS(Compare-And-Swap) 같은 동기화가 필요해져 할당 자체가 경합 지점이 된다는 것이다.

HotSpot은 이를 피하기 위해 각 스레드에게 Eden의 일부를 **전용 버퍼(TLAB)** 로 미리 떼어준다. 스레드는 자신의 TLAB 안에서는 다른 스레드와 경합할 일이 없으므로 동기화 없이 포인터만 증가시키며 할당하고, TLAB가 가득 차면 그때만 Eden 전체를 관리하는 공용 포인터에 동기화된 요청을 보내 새 TLAB를 받는다. **왜 이렇게 하면 빠른가?** 동기화가 필요한 지점을 "객체 하나 할당할 때마다"에서 "TLAB 하나를 다 썼을 때만"으로 극적으로 줄이기 때문이다.

TLAB에 담기 어려운 큰 객체는 TLAB를 거치지 않고 별도로 할당된다. Serial/Parallel처럼 물리적으로 고정된 Young/Old를 쓰는 컬렉터에서는 Eden에 직접 할당되거나(너무 크면) Old에 곧바로 할당되고, G1에서는 Region 크기의 50%를 넘는 객체를 **Humongous Object**로 분류해 전용 Humongous Region(들)에 별도로 할당한다 — 일반 Eden/Old 개념과는 구분되는 G1만의 처리 경로다.

## 약한 세대 가설과 세대별 GC

**약한 세대 가설(Weak Generational Hypothesis)**: 대부분의 객체는 생성된 직후 금방 참조를 잃고, 오래 살아남는 객체는 상대적으로 적다는 경험적 관찰이다. 이 가설에 따라 HotSpot은 힙을 **Young 세대**와 **Old 세대**로 나눈다.

```
┌─────────────────────────────┐  ┌───────────────────────┐
│           Young              │  │          Old           │
│  ┌───────┐ ┌─────┐ ┌─────┐  │  │                         │
│  │ Eden  │ │ S0  │ │ S1  │  │  │   오래 살아남은 객체       │
│  └───────┘ └─────┘ └─────┘  │  │   (승격된 객체)           │
└─────────────────────────────┘  └───────────────────────┘
```

**객체의 이동 흐름**
1. `new`로 생성된 객체는 Young의 **Eden** 영역(정확히는 할당 스레드의 TLAB)에 할당된다.
2. Eden이 차면 **Minor GC**가 발생한다 — Eden과 사용 중인 Survivor(S0 또는 S1) 중 살아남은 객체만 비어있는 다른 Survivor로 복사하고, 나머지는 통째로 비운다.
3. Minor GC에서 살아남을 때마다 객체의 **age**가 1씩 증가하며, age가 임계치(`-XX:MaxTenuringThreshold`)를 넘으면 Old 세대로 **승격(promotion)** 된다.

**왜 Survivor를 두 개(S0, S1) 두는가?** Minor GC는 매번 "현재 사용 중인 영역 → 비어있는 영역"으로 살아남은 객체를 전부 복사(copying)한다. 두 Survivor를 번갈아 쓰면 항상 한쪽은 비어 있는 상태가 보장되므로, 복사 대상 공간을 매번 새로 마련할 필요 없이 단순하고 빠르게 압축(compaction)까지 겸할 수 있다 — Sweep 이후 별도 Compact 단계 없이 복사 자체가 곧 정리다.

**왜 세대를 나누면 빠른가?** 세대 구분이 없다면 GC는 매번 힙 전체를 훑어야 한다. 하지만 가설대로 대부분의 객체가 금방 죽는다면, 신생 객체가 몰려 있는 Young만 자주 훑어도 회수되는 쓰레기의 대부분을 잡아낼 수 있다. Young은 크기가 작아 훑는 비용도 작으므로, "적은 비용으로 대부분의 쓰레기를 자주 회수"하는 전략이 성립한다. 반대로 오래 살아남아 Old로 승격된 객체들은 애초에 잘 죽지 않으므로, Old까지 포함하는 전체 훑기(Full GC)는 상대적으로 드물게만 수행해도 충분하다.

| 구분 | 대상 | 빈도 | STW 시간 |
|---|---|---|---|
| Minor GC | Young | 잦음 | 짧음 |
| Major GC | Old (GC 구현마다 정의가 조금씩 다름) | 드묾 | 김 |
| Full GC | Young + Old 전체 | 가장 드묾 | 가장 김 |

### Promotion Failure — Old 공간 부족이 Minor GC를 Full GC로 만드는 이유

Minor GC는 원래 Young만 대상으로 하는 짧은 작업이지만, 3단계(승격)에서 Old로 옮길 객체가 있는데 **Old에 그 객체들을 담을 연속 공간이 부족하면** 승격 자체가 실패한다. 이를 **Promotion Failure**라 부르며, JVM은 복구를 위해 결국 Old까지 포함한 전체 Full GC를 강제로 수행한다 — 원래 수 ms면 끝났을 Minor GC가 갑자기 수백 ms~초 단위의 Full GC로 격상되는 것이다.

G1에서는 같은 문제가 **Evacuation Failure**(로그에는 `to-space exhausted`)로 나타난다. G1의 Minor/Mixed GC는 살아있는 객체를 비어있는 Region으로 복사(evacuate)하는 방식인데, 복사할 빈 Region이 충분하지 않으면 이 복사가 실패하고 마찬가지로 Full GC로 폴백한다. **왜 튜닝에서 자주 놓치는 원인인가?** Young 영역 크기나 GC 빈도만 보고 튜닝하다가, 정작 원인은 "Old 영역이 상대적으로 작아 승격 러시를 못 받아낸다"는 점을 놓치는 경우가 많기 때문이다 — 힙 전체 크기(`-Xmx`)뿐 아니라 세대 간 비율(`-XX:NewRatio`, G1의 Region 배분)도 함께 살펴야 하는 이유다.

## GC 알고리즘 비교

| GC | 방식 | 스레드 | STW 특징 | 적합한 상황 |
|---|---|---|---|---|
| Serial GC | 세대별, 단일 스레드 | 1개 | 전체 STW | 힙이 작은 클라이언트/단일 CPU 환경 |
| Parallel GC | 세대별, 다중 스레드로 STW 단축 | 여러 개 | 전체 STW (병렬화로 시간 단축) | 처리량(throughput) 우선, Java 8 기본값 |
| CMS (Concurrent Mark Sweep) | Old 마킹·스윕을 애플리케이션과 동시 수행 | 여러 개 | 짧은 STW + concurrent 단계 | 낮은 지연시간 우선(Java 9부터 deprecated, Java 14 제거) |
| G1GC | 힙을 Region으로 분할, 가비지 많은 Region 우선 회수 | 여러 개 | 목표 시간 내 STW 제어 | 대용량 힙 + 예측 가능한 지연시간, Java 9+ 기본값 |
| ZGC / Shenandoah | Region + 컬러드 포인터/로드 배리어로 대부분 단계를 concurrent화 | 여러 개 | 수 ms 수준의 STW, 힙 크기와 무관 | 초저지연 요구, 매우 큰 힙 |

**시대별 기본 GC 변화**: Java 8까지는 처리량 위주의 Parallel GC가 기본이었으나, 애플리케이션 힙이 커지고 지연시간에 대한 요구가 커지면서 Java 9부터 G1GC가 기본 GC로 바뀌었다. ZGC(Java 15 production)와 Shenandoah는 "STW 시간이 힙 크기에 비례하지 않는다"는 목표로 설계된 더 최신 세대다.

### CMS의 4단계와 폐지 이유

CMS는 Old 영역을 다음 순서로 수집한다.

1. **Initial Mark** (STW, 짧음) — GC Root가 **직접** 참조하는 객체만 빠르게 마킹한다.
2. **Concurrent Mark** (동시 수행) — Initial Mark에서 찾은 객체들로부터 참조 그래프 전체를 애플리케이션과 동시에 순회하며 마킹한다.
3. **Remark** (STW, Concurrent Mark보다는 짧음) — Concurrent Mark 도중 애플리케이션이 참조 관계를 바꿨을 수 있으므로(Card Table에 기록된 변경분을 이용해) 마킹 결과를 다시 멈춰서 보정·확정한다.
4. **Concurrent Sweep** (동시 수행) — 마킹되지 않은 객체를 애플리케이션과 동시에 회수한다.

**왜 결국 폐지됐는가?** Concurrent Sweep에는 살아있는 객체를 이동시켜 정리하는 **Compact 단계가 없다.** 회수는 하되 빈 공간을 재배치하지 않으므로 힙 곳곳에 작은 빈 조각들만 남는 단편화가 사이클마다 누적된다. 단편화가 심해져 큰 객체를 넣을 연속 공간이 사라지면, CMS는 어쩔 수 없이 STW 상태로 힙 전체를 압축하는 **`concurrent mode failure`** 를 일으킨다 — 평소엔 지연시간이 짧다가 예고 없이 매우 긴 Full GC가 튀어나오는 예측 불가능성이 CMS가 G1으로 대체되고 결국 제거된 핵심 이유다.

## G1GC 상세

G1(Garbage-First)은 힙을 물리적으로 고정된 Young/Old 블록으로 나누지 않고, 수백~수천 개의 균일한 크기 **Region**으로 쪼갠다. 각 Region은 논리적으로 Eden, Survivor, Old, 그리고 큰 객체 전용인 Humongous 역할을 동적으로 부여받는다.

```
[Eden][Old][Eden][Survivor][Old][Eden][Humongous][Old]...
 ← Region 하나하나는 역할이 고정되지 않고 필요에 따라 재배정된다
```

**왜 Region으로 나누는가?** 기존 GC들은 Young GC를 하든 Old GC를 하든 그 세대에 속한 영역 전체를 대상으로 해야 했다. G1은 각 Region마다 "이 Region을 회수하면 얼마나 많은 가비지를 얻는가"를 추적해두고, 사용자가 지정한 목표 정지시간(`-XX:MaxGCPauseMillis`) 안에서 **가비지 비율이 가장 높은 Region들만 골라** 회수한다. 즉 "전체를 다 훑는 대신, 청소했을 때 이득이 가장 큰 곳부터 청소한다"는 전략으로 STW 시간을 예측 가능한 범위 안에 묶어둔다 — 이름 자체가 이 우선순위 전략(Garbage **First**)에서 나왔다. Young Region만 회수하는 Minor GC 외에, Young과 가비지 비율이 높은 일부 Old Region을 함께 회수하는 **Mixed GC**가 G1의 특징적인 중간 단계다.

**Remembered Set과 Card Table**: Young Region만 회수하는 Minor GC라도, Old Region에 있는 객체가 Young Region의 객체를 참조하고 있을 수 있다(예: Old 객체의 필드가 방금 생성된 Young 객체를 가리키는 경우). 이 경우를 놓치지 않으려면 원칙적으로 Old 전체를 훑어 Young을 참조하는 지점을 찾아야 하는데, 그러면 Young GC가 더 이상 빠르지 않다. G1은 각 Region마다 **Remembered Set**(RSet)을 두어 "어떤 다른 Region이 나를 참조하고 있는지"를 미리 기록해둔다.

이 RSet을 실시간으로 정확히 유지하는 대신, 힙 전체를 512바이트 단위의 "카드(Card)"로 나눈 **Card Table**과 **Write Barrier**를 함께 쓴다. 참조 필드에 값을 대입하는 모든 바이트코드 뒤에는 컴파일러가 삽입한 코드(Write Barrier)가 붙어, 그 필드가 속한 카드를 "더러움(dirty)"으로 표시만 하고 즉시 RSet을 갱신하지는 않는다. 별도의 **동시 정제(Concurrent Refinement) 스레드**가 이 dirty card 큐를 백그라운드에서 처리하며 실제 RSet을 갱신한다. **왜 이렇게 두 단계로 나누는가?** 참조를 대입할 때마다 즉시 RSet을 갱신하면 애플리케이션 스레드가 매 대입 연산마다 그 비용을 직접 떠안게 된다. 일단 "더러워졌다"는 표시만 저렴하게 남기고, 실제 정리는 백그라운드 스레드에 위임함으로써 애플리케이션 스레드의 실행 경로에서 무거운 작업을 덜어낸다.

**SATB (Snapshot-At-The-Beginning)**: G1의 Old 영역 동시 마킹(concurrent marking)은 애플리케이션 스레드와 동시에 진행되므로, 마킹 도중 애플리케이션이 참조 관계를 바꿀 수 있다. SATB는 마킹을 시작하는 시점의 객체 그래프를 논리적 스냅샷으로 간주하고, 그 이후 끊어지는 참조가 있더라도 일단 "마킹 시작 시점에 살아있었던 객체"는 이번 사이클에서는 살아있는 것으로 취급한다(다음 사이클에서 정리된다). 이 보수적인 처리 덕분에 동시 마킹 중에도 정확성을 잃지 않고 애플리케이션을 멈추지 않을 수 있다.

## STW를 줄이는 방향 — Concurrent GC로의 진화

전통적인 GC(Serial, Parallel)는 Mark, Sweep, Compact를 모두 애플리케이션을 완전히 멈춘(Stop-The-World) 상태에서 수행한다. 이후 세대의 GC들은 이 STW 구간을 점점 좁혀가는 방향으로 발전했다.

- **CMS**: Old의 Mark/Sweep을 애플리케이션과 동시에 수행해 STW를 줄였지만, 앞서 다룬 대로 Compact 단계가 없어 결국 예측 불가능한 `concurrent mode failure`를 피할 수 없었다.
- **G1**: Region 단위 복사(copying) 방식을 쓰기 때문에 회수와 동시에 압축 효과를 얻는다(Young GC의 Survivor 복사와 원리가 같다). CMS의 단편화 문제를 구조적으로 피하면서, 목표 정지시간 기반으로 STW를 관리한다.
- **ZGC / Shenandoah**: 컬러드 포인터(colored pointer)·로드 배리어(load barrier) 같은 기법으로 마킹뿐 아니라 **압축(재배치)** 단계까지 애플리케이션 스레드와 동시에 수행한다. 객체가 옮겨지는 도중에도 애플리케이션 스레드가 안전하게 그 객체에 접근할 수 있도록 참조 자체에 GC 상태 정보를 인코딩해두는 방식이다. 그 결과 STW는 루트 스캔처럼 아주 짧은 단계에만 남아, 힙이 수십~수백 GB로 커져도 STW 시간이 거의 늘지 않는다.

결국 GC의 발전사는 "어떻게 하면 애플리케이션을 멈추는 시간을 힙 크기와 무관하게 만들 것인가"라는 하나의 목표를 향해 있다 — Serial/Parallel(전부 멈춤) → CMS(마킹만 동시, 압축은 여전히 멈춤) → G1(목표 시간 내로 멈춤 시간 관리) → ZGC/Shenandoah(압축까지 거의 동시)로 이어지는 흐름이다.

## GC 로그 읽는 법

Java 9부터 통합된 `-Xlog:gc` 옵션(Unified JVM Logging)으로 GC 로그를 남길 수 있다. G1 기준 대표적인 한 줄은 다음과 같은 정보를 담는다.

```
[12.345s][info][gc] GC(42) Pause Young (Normal) (G1 Evacuation Pause) 512M->128M(1024M) 15.234ms
```

- `[12.345s]` — JVM 시작 후 경과 시간
- `GC(42)` — 42번째로 발생한 GC 사이클의 식별자
- `Pause Young (Normal) (G1 Evacuation Pause)` — GC 종류. `Pause Young`(Minor), `Pause Young (Mixed)`, `Pause Full` 등으로 구분된다
- `512M->128M(1024M)` — GC 시작 시 힙 사용량 → GC 종료 후 힙 사용량 (괄호 안은 전체 힙 용량)
- `15.234ms` — 이 GC가 애플리케이션을 멈춘 STW 시간

**실무에서 무엇을 보는가?** `Pause Full`이 로그에 등장하는 빈도와, 각 Pause의 STW 시간 분포(특히 튀는 값)를 우선 본다. Full GC가 주기적으로 반복된다면 Old 영역이나 힙 전체가 작다는 신호이고, Minor GC인데도 STW가 튄다면 앞서 다룬 Promotion Failure나 과도한 Root 스캔 비용(스레드 수가 매우 많은 경우) 등을 의심해볼 수 있다.

**흔한 실무 튜닝: `-Xms`와 `-Xmx`를 왜 같게 맞추는가** 힙은 `-Xms`(초기 크기)에서 시작해 필요에 따라 `-Xmx`(최대 크기)까지 늘어난다. 문제는 이 힙 크기 조정(resize) 자체가 STW를 유발할 수 있다는 점이다 — 운영 중인 서비스에서 트래픽이 늘 때마다 힙이 커지며 예기치 못한 지연이 튀는 걸 피하려고, 처음부터 `-Xms`와 `-Xmx`를 동일하게 맞춰 힙 크기를 고정하고 리사이즈 자체를 없애는 게 흔한 관행이다.

## Summary

- 메모리 관리의 목표는 한정된 물리 메모리를 여러 프로세스가 **안전하게(보호) · 효율적으로(활용률) · 각자 전용인 것처럼(추상화)** 쓰게 하는 것이다 — 그 핵심 장치가 **가상 주소와 MMU**다
- 연속 할당은 외부 단편화, 고정 분할은 내부 단편화 문제를 낳고, 이를 풀기 위해 메모리를 고정 크기로 쪼개는 **페이징**이 표준이 되었다. 페이징은 외부 단편화를 없애는 대신 **페이지 테이블 비용**(메모리 · 추가 접근)을 만들고, 이를 **TLB**와 **다단계 페이지 테이블**이 완화한다
- 가상 메모리는 "필요한 페이지만 물리 메모리에 올리는" **요구 페이징**으로 동작한다 — 프로세스 전체가 메모리에 없어도 실행되고, 없는 페이지에 접근하면 **페이지 폴트**가 발생해 OS가 디스크에서 가져온다
- 물리 메모리가 가득 차면 **페이지 교체 알고리즘**(FIFO · LRU · Clock)이 희생 페이지를 고른다. 교체가 너무 잦아 CPU가 일은 못 하고 페이지 입출력만 하는 상태가 **스래싱**이다
- 성능은 결국 **페이지 폴트율**이 결정한다 — 폴트 1번이 메모리 접근보다 수만~수십만 배 느리므로, 폴트율을 조금만 낮춰도 평균 접근 시간이 크게 달라진다

## 메모리 계층과 OS의 역할

CPU가 직접 접근할 수 있는 저장소는 레지스터, 캐시, 메인 메모리뿐이다. 프로그램은 실행되려면 반드시 메인 메모리에 올라와 있어야 하고, 메모리는 한정되어 있으므로 OS가 다음을 책임진다.

| 역할 | 설명 |
|---|---|
| 할당 / 회수 | 프로세스에 메모리를 나눠주고, 종료 시 회수 |
| 보호(Protection) | 한 프로세스가 다른 프로세스나 커널의 메모리를 침범하지 못하게 차단 |
| 추상화 | 각 프로세스에 연속적이고 독립된 주소 공간을 제공 |
| 활용률 | 실제 물리 메모리보다 큰 프로그램도 실행 가능하게 (가상 메모리) |

## 주소 공간과 주소 바인딩

### 논리 주소와 물리 주소

| 구분 | 설명 |
|---|---|
| 논리(가상) 주소 | 프로세스가 보는 주소. 프로세스마다 0부터 시작하는 독립된 공간 |
| 물리 주소 | 실제 메모리(RAM) 하드웨어상의 주소 |

논리 주소를 물리 주소로 바꾸는 일은 CPU 안의 하드웨어인 **MMU(Memory Management Unit)** 가 **실행 시간에** 수행한다. 컴파일 시점이나 적재 시점에 주소를 고정(바인딩)하면 프로세스를 다른 위치로 옮길 수 없지만, 실행 시점 바인딩은 프로세스를 메모리 어디에나 배치하고 나중에 옮길 수도 있게 해준다.

```text
CPU ──논리 주소──▶ [ MMU ] ──물리 주소──▶ 메모리
                     │
              (기준/한계 레지스터 또는 페이지 테이블)
```

가장 단순한 MMU는 **재배치(base) 레지스터 + 한계(limit) 레지스터**다. 논리 주소가 limit보다 작은지 검사(보호)하고, 통과하면 base를 더해 물리 주소를 만든다.

### 스와핑

메모리가 부족할 때 프로세스 전체(또는 일부)를 디스크의 **스왑 영역**으로 내보내고(swap out), 필요할 때 다시 불러오는(swap in) 기법이다. 현대 OS는 프로세스 전체가 아니라 **페이지 단위**로 내보내는 방식을 주로 쓴다.

## 연속 메모리 할당

프로세스 하나를 메모리의 **연속된 한 덩어리**에 올리는 방식이다.

### 할당 전략 (가변 분할)

빈 공간(hole) 목록에서 요청 크기에 맞는 곳을 고르는 방법이다.

| 전략 | 방식 | 특징 |
|---|---|---|
| First-fit | 처음 맞는 hole | 빠르고 보통 충분히 좋음 |
| Best-fit | 가장 작게 남는 hole | 전체 탐색 필요, 아주 작은 자투리 hole이 많이 생김 |
| Worst-fit | 가장 큰 hole | 남는 hole이 쓸만하길 기대하지만 보통 성능이 나쁨 |

### 단편화

| 종류 | 설명 | 발생 |
|---|---|---|
| 내부 단편화 | 할당받은 공간 **안에서** 쓰지 못하고 낭비되는 부분 | 고정 크기 단위로 할당할 때 |
| 외부 단편화 | 빈 공간 총합은 충분한데 **연속되지 않아** 할당 못 하는 상태 | 가변 크기 연속 할당 |

외부 단편화는 **컴팩션**(흩어진 hole을 한쪽으로 모으기)으로 해결할 수 있지만, 프로세스를 옮겨야 하므로 비용이 크다. 그래서 프로세스를 **연속되지 않게** 배치할 수 있는 방식, 즉 페이징과 세그멘테이션이 등장했다.

## 페이징(Paging)

물리 메모리를 고정 크기의 **프레임**(frame), 논리 메모리를 같은 크기의 **페이지**(page)로 나눈다. 페이지를 어느 프레임에 넣어도 되므로 프로세스가 물리적으로 흩어져 있어도 논리적으로는 연속인 것처럼 보인다.

```text
논리 주소 = [ 페이지 번호 p | 오프셋 d ]

페이지 테이블: p → 프레임 번호 f
물리 주소 = [ 프레임 번호 f | 오프셋 d ]
```

예를 들어 페이지 크기가 4KB(2¹²)면 하위 12비트가 오프셋이고, 나머지 상위 비트가 페이지 번호다. 오프셋은 변환되지 않고 그대로 쓰인다.

**특징**
- 외부 단편화가 없다. 다만 마지막 페이지에서 **내부 단편화**가 평균 반 페이지 정도 생긴다
- 페이지 크기가 작으면 내부 단편화는 줄지만 페이지 테이블이 커진다. 페이지 크기는 이 둘의 절충이다 (현대 x86 · ARM에서 기본 4KB)
- 페이지 테이블은 **프로세스마다** 하나씩 가지며, 프로세스 문맥 교환 시 테이블 기준 레지스터(x86의 CR3)가 바뀐다

### 페이지 테이블 엔트리(PTE)

프레임 번호 외에 제어 비트가 함께 들어 있다.

| 비트 | 의미 |
|---|---|
| Valid / Present | 이 페이지가 물리 메모리에 있는가 (없으면 접근 시 페이지 폴트) |
| Read / Write / Execute | 접근 권한 — 보호의 핵심 |
| Dirty | 메모리에 올라온 뒤 수정되었는가 (교체 시 디스크에 써야 하는지 판단) |
| Accessed (Reference) | 최근 접근되었는가 (교체 알고리즘이 사용) |

### TLB (Translation Lookaside Buffer)

페이지 테이블 자체가 메모리에 있으므로, 변환 없이는 **데이터 한 번 읽는 데 메모리를 두 번 접근**(테이블 + 실제 데이터)해야 한다. 이를 막기 위해 최근 변환 결과를 MMU 옆의 빠른 캐시에 저장해 두는 것이 TLB다.

```text
TLB hit  → 페이지 테이블 접근 없이 바로 물리 주소 (빠름)
TLB miss → 페이지 테이블을 조회한 뒤 TLB에 채움
```

유효 접근 시간(EAT)은 **적중률(hit ratio)** 에 좌우된다. 메모리 접근 100ns, TLB 접근 10ns, 적중률 98%라면 다음과 같다.

```text
EAT = 0.98 × (10 + 100) + 0.02 × (10 + 100 + 100) = 112ns
```

(미스 시에는 페이지 테이블 1회 + 데이터 1회가 더 필요하다. 단일 단계 페이지 테이블을 가정한 계산이다.)

TLB는 프로세스마다 변환 결과가 다르므로 **문맥 교환 시 비우거나**, 엔트리에 프로세스 식별자(ASID/PCID)를 붙여 구분한다. 문맥 교환 직후 성능이 잠시 떨어지는 이유다.

### 페이지 테이블 크기 문제와 다단계 페이지 테이블

64비트 주소 공간을 단일 배열 테이블로 표현하면 테이블이 비현실적으로 커진다. 대부분의 프로세스는 주소 공간의 극히 일부만 쓰므로, 테이블도 **쓰는 부분만** 만들면 된다.

| 방식 | 설명 |
|---|---|
| 다단계(계층) 페이지 테이블 | 테이블을 트리로 만들고, 사용하는 영역의 하위 테이블만 생성 |
| 해시 페이지 테이블 | 가상 페이지 번호를 해시해 조회 (넓은 주소 공간에 적합) |
| 역 페이지 테이블 | **물리 프레임마다** 엔트리 하나. 테이블은 작지만 조회에 해시 등이 필요하고 공유가 어려움 |

x86-64 Linux는 기본적으로 48비트 가상 주소에 **4단계** 페이지 테이블을 쓴다. 각 단계가 9비트씩 인덱스를 맡고 하위 12비트가 오프셋이다 (9×4 + 12 = 48). 단계가 늘어나면 TLB miss 시 접근 횟수도 늘어나므로, 결국 **TLB 적중률이 중요**해진다.

## 세그멘테이션(Segmentation)

메모리를 **의미 단위**(코드, 데이터, 힙, 스택 등)로 나누는 방식이다. 주소는 `[세그먼트 번호, 오프셋]`으로 표현되고, 세그먼트마다 base와 limit을 가진다.

| 구분 | 페이징 | 세그멘테이션 |
|---|---|---|
| 분할 단위 | 고정 크기 | 가변 크기 (논리적 단위) |
| 사용자 인식 | 보이지 않음 (OS가 투명하게 처리) | 프로그래머/컴파일러가 의식하는 단위 |
| 단편화 | 내부 단편화 | 외부 단편화 |
| 보호·공유 | 페이지 단위 | 세그먼트 단위로 자연스러움 (코드 세그먼트 공유 등) |

순수 세그멘테이션은 외부 단편화 때문에 현대 OS에서 거의 쓰이지 않는다. 현대 x86-64 Linux는 사실상 **페이징만** 사용하고 세그먼트는 평평하게(flat) 설정한다. 다만 세그멘테이션의 "의미 단위로 권한을 나눈다"는 아이디어는 페이징 위에서 **프로세스 주소 공간의 영역 구분**으로 이어진다.

```text
높은 주소  ┌──────────────┐
          │   Stack      │ ↓ 아래로 성장
          │      ...     │
          │   Heap       │ ↑ 위로 성장 (malloc, new)
          │   Data / BSS │ 전역·정적 변수
          │   Code(Text) │ 실행 코드 (읽기 전용)
낮은 주소  └──────────────┘
```

## 가상 메모리와 요구 페이징

### 왜 가상 메모리인가

프로그램의 모든 코드와 데이터가 동시에 필요한 것은 아니다. 에러 처리 루틴, 거의 안 쓰는 기능, 큰 배열의 일부는 실행 내내 접근되지 않을 수 있다. 가상 메모리는 **필요한 부분만 물리 메모리에 올려** 다음 효과를 얻는다.

- 물리 메모리보다 큰 프로그램 실행 가능
- 같은 메모리에 더 많은 프로세스를 동시에 올려 CPU 활용률 향상
- 프로세스 간 공유 메모리, 파일 매핑(`mmap`) 같은 기능의 기반

### 요구 페이징 (Demand Paging)

페이지가 **실제로 접근될 때** 비로소 메모리에 적재한다. PTE의 Valid 비트가 0인 페이지에 접근하면 **페이지 폴트**(page fault)가 발생한다.

```text
1. CPU가 가상 주소 접근 → MMU가 PTE 확인 → Valid = 0 → 트랩(페이지 폴트)
2. OS가 접근이 유효한 주소인지 검사 (무효면 프로세스 종료, SIGSEGV)
3. 비어 있는 프레임을 찾는다 (없으면 페이지 교체)
4. 디스크에서 해당 페이지를 그 프레임으로 읽어온다 (I/O, 프로세스는 대기)
5. PTE를 갱신 (프레임 번호, Valid = 1)
6. 폴트를 일으킨 명령어를 재실행
```

페이지 폴트는 두 종류로 나눠 볼 수 있다.

| 종류 | 설명 | 비용 |
|---|---|---|
| Minor fault | 디스크 I/O 없이 해결 (이미 메모리에 있는 페이지 매핑, 0으로 채운 페이지 할당 등) | 작음 |
| Major fault | 디스크에서 읽어와야 함 | 매우 큼 |

### 페이지 폴트가 성능에 미치는 영향

메모리 접근 200ns, 폴트 처리 8ms(= 8,000,000ns)라 하면 폴트율 *p*에 대해 다음과 같다.

```text
EAT = (1 - p) × 200 + p × 8,000,000 (ns)
p = 1/1000 일 때 → 약 8,200ns  (정상 대비 약 40배 느려짐)
```

폴트가 1,000번에 1번만 나도 40배 느려진다. 성능 저하를 10% 이내로 막으려면 폴트율이 약 2,500,000번에 1번 이하여야 한다. **폴트율을 극단적으로 낮게 유지하는 것**이 가상 메모리 설계의 핵심이다.

### Copy-on-Write (COW)

`fork()`로 자식 프로세스를 만들 때 부모의 메모리를 전부 복사하면 낭비가 크다. 대신 **페이지를 공유(읽기 전용)** 하다가 누군가 **쓰기**를 시도하는 순간 해당 페이지만 복사한다. 자식이 곧바로 `exec()`를 호출하는 흔한 경우에는 복사가 거의 일어나지 않아 `fork()`가 빠르다.

## 페이지 교체

물리 메모리에 빈 프레임이 없을 때 **희생 페이지(victim)** 를 골라 내보내야 한다. 희생 페이지가 Dirty면 디스크에 써야 하므로(I/O 2회), 깨끗한 페이지를 내보내는 편이 싸다.

### 교체 알고리즘

| 알고리즘 | 방식 | 특징 |
|---|---|---|
| OPT (최적) | **앞으로 가장 오래 쓰이지 않을** 페이지 | 폴트 수가 최소지만 미래를 알아야 해 구현 불가 → 다른 알고리즘의 **비교 기준** |
| FIFO | 가장 먼저 들어온 페이지 | 구현이 단순하지만 자주 쓰는 페이지도 내보냄. **Belady의 모순** 발생 가능 |
| LRU | **가장 오래 사용되지 않은** 페이지 | 과거를 미래의 근사로 사용, 성능 좋음. 정확한 구현은 하드웨어 비용이 큼 |
| Clock (Second-chance) | 원형 큐 + 참조 비트 | LRU의 저렴한 근사. 참조 비트가 1이면 0으로 바꾸고 한 번 더 기회를 줌 |

**Belady의 모순**: FIFO에서는 프레임 수를 **늘렸는데 오히려 폴트가 늘어나는** 경우가 있다. 참조열 `1 2 3 4 1 2 5 1 2 3 4 5`에서 프레임이 3개면 폴트가 9번, 4개면 10번이다. LRU와 OPT처럼 "N개 프레임의 페이지 집합이 N+1개 프레임의 부분집합"이 성립하는 스택 알고리즘에서는 발생하지 않는다.

LRU의 정확한 구현(타임스탬프 갱신이나 스택 조작)은 메모리 접근마다 비용이 들어 현실적이지 않다. 그래서 실제 OS는 **참조 비트**를 이용한 Clock 계열 근사를 쓴다. Linux도 active/inactive 리스트에 참조 비트를 결합한 LRU 근사 방식을 사용한다.

### 프레임 할당과 교체 범위

| 구분 | 설명 |
|---|---|
| 전역 교체 | 모든 프로세스의 페이지 중에서 희생자를 고름. 유연하지만 한 프로세스가 다른 프로세스 성능에 영향 |
| 지역 교체 | 자기 프로세스에 할당된 프레임 안에서만 교체. 예측 가능하지만 프레임을 못 빌려 씀 |

## 스래싱(Thrashing)

프로세스가 필요로 하는 페이지를 담을 만큼의 프레임이 없어 **페이지 폴트가 연쇄적으로** 발생하고, CPU 시간 대부분을 페이지 입출력에 쓰는 상태다.

```text
다중 프로그래밍 정도 ↑
  → 프로세스당 프레임 ↓
  → 페이지 폴트 ↑
  → I/O 대기 ↑, CPU 사용률 ↓
  → OS가 "CPU가 놀고 있네" 하고 프로세스를 더 투입
  → 악순환
```

### 지역성과 워킹 셋

스래싱을 이해하려면 **지역성(locality)** 이 핵심이다. 프로세스는 어느 시점에 **특정 페이지 집합**에 집중해 접근한다(시간 지역성 · 공간 지역성). 이 집합이 워킹 셋(working set)이다.

| 대응 방법 | 설명 |
|---|---|
| 워킹 셋 모델 | 최근 Δ번의 접근에서 쓰인 페이지 집합을 프레임에 유지. 워킹 셋 총합이 물리 메모리를 넘으면 프로세스를 일시 중단(swap out) |
| 페이지 폴트 빈도(PFF) | 폴트율의 상한/하한을 정해, 높으면 프레임을 더 주고 낮으면 회수 |
| 다중 프로그래밍 정도 조절 | 동시에 실행하는 프로세스 수를 줄임 |

## 실무에서 만나는 메모리 이슈

**1. 스왑이 일어나기 시작하면 응답 시간이 급격히 나빠진다**

서버에서 메모리가 부족해 스왑이 활발해지면 사실상 스래싱에 가깝다. 지연에 민감한 서비스는 스왑을 줄이거나(`vm.swappiness` 조정) 끄고, 메모리 한도를 모니터링한다.

**2. JVM 힙과 물리 메모리**

JVM의 `-Xmx`로 정한 힙은 **가상 주소 공간**에 예약된 크기고, 실제로 접근된 페이지만 물리 메모리를 차지한다(요구 페이징). 하지만 [GC](/dev/jvm)가 힙 전체를 훑거나 힙의 일부가 스왑 아웃되면 GC 중에 페이지 폴트가 쏟아져 Stop-The-World 시간이 길어진다. 컨테이너 환경에서는 힙 외에 스레드 스택, 메타스페이스, 네이티브 메모리까지 합쳐 **메모리 한도 안에 들어가야** 한다.

**3. OOM Killer**

Linux는 메모리 오버커밋을 허용한다. 약속한 가상 메모리가 실제로 사용되어 물리 메모리와 스왑이 모두 고갈되면, 커널이 점수가 높은 프로세스를 골라 **강제 종료(OOM Killer)** 한다. 컨테이너에서 메모리 한도(cgroup)를 넘기면 해당 컨테이너의 프로세스가 같은 방식으로 종료된다 (`OOMKilled`).

**4. `fork()`와 COW**

Redis가 RDB 스냅샷을 만들 때 `fork()`한 자식 프로세스가 부모와 메모리를 COW로 공유한다. 이때 부모가 쓰기를 많이 하면 변경된 페이지가 복사되어 **메모리 사용량이 최대 2배 가까이** 늘 수 있다.

## 정리 — 한눈에 보기

```text
주소 변환:  논리 주소 ─(MMU: 페이지 테이블 + TLB)─▶ 물리 주소
                            │
              Valid = 0 ────┴─▶ 페이지 폴트 → OS가 디스크에서 로드
                                                    │
                                     빈 프레임 없음 ─┴─▶ 페이지 교체 (LRU/Clock)
                                                          └─ 너무 잦으면 스래싱
```

| 문제 | 해결책 |
|---|---|
| 프로세스 간 침범 | 주소 공간 분리 + PTE 권한 비트 |
| 외부 단편화 | 페이징 |
| 페이지 테이블이 큼 | 다단계 페이지 테이블 |
| 변환이 느림 | TLB |
| 물리 메모리보다 큰 프로그램 | 가상 메모리 + 요구 페이징 |
| 메모리 부족 | 페이지 교체, 스왑 |
| 스래싱 | 워킹 셋 / PFF / 다중 프로그래밍 정도 조절 |

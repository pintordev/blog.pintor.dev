## Summary

- SOLID는 "변경이 일어났을 때 수정 범위를 작게 가두는" 다섯 가지 설계 기준이다 — 목표는 높은 응집도와 낮은 결합도 하나로 수렴한다
- SRP의 "책임"은 기능 개수가 아니라 **변경의 이유(액터)** 다 — 메서드가 많아도 변경 이유가 하나면 SRP를 지킨 것이다
- OCP는 `if/else`를 없애자는 규칙이 아니라, **변경이 예상되는 지점에만 추상화를 두자**는 규칙이다 — 모든 곳에 적용하면 과설계가 된다
- LSP는 상속의 문법(is-a)이 아니라 **행동 계약**의 문제다 — 컴파일되더라도 사전/사후조건이 깨지면 위반이다
- ISP는 인터페이스를 **클라이언트(사용하는 쪽) 관점**에서 쪼개는 것이고, DIP는 **의존성의 소유권과 방향**을 뒤집는 것이다
- 다섯 원칙은 서로 맞물린다 — LSP가 OCP의 전제 조건이고, DIP가 OCP를 실제로 가능하게 하는 메커니즘이다
- 원칙은 법칙이 아니라 **트레이드오프** 도구다 — 변경이 실제로 발생하는 지점에서 적용해야 효과가 있다

## SOLID란

로버트 C. 마틴(Uncle Bob)이 정리한 객체지향 설계 원칙 다섯 가지의 앞 글자를 딴 약어다.

| 원칙 | 이름 | 한 줄 설명 |
|---|---|---|
| SRP | 단일 책임 원칙 | 클래스는 변경되는 이유가 하나뿐이어야 한다 |
| OCP | 개방-폐쇄 원칙 | 확장에는 열려 있고, 수정에는 닫혀 있어야 한다 |
| LSP | 리스코프 치환 원칙 | 하위 타입은 상위 타입을 대체할 수 있어야 한다 |
| ISP | 인터페이스 분리 원칙 | 클라이언트는 쓰지 않는 메서드에 의존하면 안 된다 |
| DIP | 의존관계 역전 원칙 | 구체가 아닌 추상에 의존해야 한다 |

**왜 필요한가?** 소프트웨어는 한 번 만들고 끝나는 게 아니라 계속 변경된다. 변경 하나가 여러 클래스로 연쇄 전파(ripple effect)되고, 관련 없는 기능이 함께 깨진다면 설계가 변경에 취약하다는 뜻이다. SOLID는 그 취약성이 생기는 대표적인 패턴을 다섯 가지 관점에서 막는 기준이다.

## SRP — 단일 책임 원칙

> A module should be responsible to one, and only one, actor.

"하나의 일만 한다"로 흔히 요약되지만, 마틴이 말한 본래 의미는 **변경을 요구하는 주체(액터)가 하나여야 한다**는 것이다.

```java
// 위반: 서로 다른 액터의 요구가 한 클래스에 섞여 있다
class Employee {
    Money calculatePay() { ... }    // 회계팀이 규칙을 바꾼다
    String reportHours() { ... }    // 인사팀이 규칙을 바꾼다
    void save() { ... }             // DBA/개발팀이 저장 방식을 바꾼다
}
```

`calculatePay()`와 `reportHours()`가 같은 private 메서드 `calculateRegularHours()`를 공유한다고 하자. 회계팀 요구로 이 공통 메서드를 고치면 인사팀 보고서까지 의도치 않게 바뀐다. 이것이 SRP 위반이 실제로 일으키는 사고다.

```java
// 준수: 액터별로 분리, 데이터만 공유
class PayCalculator   { Money calculatePay(Employee e) { ... } }
class HourReporter    { String reportHours(Employee e) { ... } }
class EmployeeRepository { void save(Employee e) { ... } }
```

**자주 하는 오해**

| 오해 | 실제 |
|---|---|
| 메서드는 하나만 가져야 한다 | 메서드 개수와 무관하다. 변경 이유가 하나인지가 기준 |
| 클래스를 잘게 쪼갤수록 좋다 | 같이 바뀌는 것을 억지로 떼어놓으면 응집도가 오히려 떨어진다 |

SRP는 응집도 관점에서 "**같은 이유로 바뀌는 것은 모으고, 다른 이유로 바뀌는 것은 분리하라**"로 정리할 수 있다.

## OCP — 개방-폐쇄 원칙

> Software entities should be open for extension, but closed for modification.

새 기능을 추가할 때 **기존 코드를 수정하지 않고** 새 코드를 추가하는 것만으로 해결할 수 있어야 한다.

```java
// 위반: 할인 정책이 추가될 때마다 기존 메서드를 수정
long discount(Customer c, long price) {
    if (c.grade() == GOLD)   return price * 20 / 100;
    if (c.grade() == SILVER) return price * 10 / 100;
    // VIP 추가 → 여기를 또 수정, 기존 분기가 깨질 위험
    return 0;
}

// 준수: 추상화에 의존하고, 새 정책은 클래스 추가로 해결
interface DiscountPolicy { long discount(long price); }
class GoldDiscount   implements DiscountPolicy { ... }
class SilverDiscount implements DiscountPolicy { ... }
class VipDiscount    implements DiscountPolicy { ... }  // 기존 코드 수정 없음

class OrderService {
    private final DiscountPolicy policy;  // 구체 정책을 모른다
    long pay(long price) { return price - policy.discount(price); }
}
```

**핵심은 "어디를 닫을 것인가"** 다. 모든 변경을 예측해 추상화하는 것은 불가능하고, 불필요한 추상화는 복잡도만 늘린다. 실무에서는 다음 순서가 현실적이다.

1. 처음에는 단순하게 구현한다
2. 같은 종류의 변경이 반복되는 지점을 발견한다 (분기가 계속 늘어난다)
3. 그 지점에 추상화(전략 패턴 등)를 도입한다

OCP를 구현하는 대표적인 수단은 **다형성**(전략, 템플릿 메서드, 데코레이터 패턴)이고, 이를 가능하게 하는 메커니즘이 아래 LSP와 DIP다.

## LSP — 리스코프 치환 원칙

> 하위 타입은 언제나 자신의 상위 타입으로 교체될 수 있어야 한다. (Barbara Liskov)

상속은 컴파일러가 보장하는 **문법적 관계**이고, LSP는 그 위에서 **행동의 호환성**을 요구한다.

```java
class Rectangle {
    protected int width, height;
    void setWidth(int w)  { this.width = w; }
    void setHeight(int h) { this.height = h; }
    int area() { return width * height; }
}

class Square extends Rectangle {
    @Override void setWidth(int w)  { this.width = w; this.height = w; }
    @Override void setHeight(int h) { this.width = h; this.height = h; }
}

void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert r.area() == 20;  // Square가 들어오면 16 → 실패
}
```

수학적으로 정사각형은 직사각형이지만, "가로와 세로를 독립적으로 바꿀 수 있다"는 `Rectangle`의 **암묵적 계약**을 `Square`가 깨뜨린다. 상위 타입을 믿고 작성된 `resize()`가 하위 타입 앞에서 무너지므로 LSP 위반이다.

**LSP를 지키기 위한 규칙 (계약에 의한 설계)**

| 항목 | 규칙 |
|---|---|
| 사전조건(precondition) | 하위 타입이 **강화**할 수 없다 (더 까다로운 입력 요구 불가) |
| 사후조건(postcondition) | 하위 타입이 **약화**할 수 없다 (더 부실한 결과 보장 불가) |
| 불변식(invariant) | 상위 타입의 불변식을 유지해야 한다 |
| 예외 | 상위 타입이 선언하지 않은 새 예외를 던지면 안 된다 |

**위반 신호**: 하위 클래스에서 `UnsupportedOperationException`을 던진다, 메서드를 빈 구현으로 오버라이딩한다, 호출부에서 `instanceof`로 타입을 확인해 분기한다.

**OCP와의 관계**: 하위 타입이 상위 타입을 완벽히 대체할 수 없다면, 호출부는 결국 타입별 분기(`instanceof`)를 넣어야 하고 이는 OCP 위반으로 번진다. 즉 LSP는 OCP의 전제 조건이다. (오버라이딩 시 접근 제어자·반환 타입 규칙이 LSP에서 나온다는 점은 [OOP 정리](/dev/oop/) 참고)

## ISP — 인터페이스 분리 원칙

> 클라이언트는 자신이 사용하지 않는 메서드에 의존하도록 강요받아서는 안 된다.

```java
// 위반: 뚱뚱한 인터페이스
interface MultiFunctionDevice {
    void print(Document d);
    void scan(Document d);
    void fax(Document d);
}

class SimplePrinter implements MultiFunctionDevice {
    public void print(Document d) { ... }
    public void scan(Document d)  { throw new UnsupportedOperationException(); }  // 억지 구현
    public void fax(Document d)   { throw new UnsupportedOperationException(); }
}

// 준수: 역할 단위로 분리
interface Printer { void print(Document d); }
interface Scanner { void scan(Document d); }
interface Fax     { void fax(Document d); }

class SimplePrinter implements Printer { ... }
class AllInOne implements Printer, Scanner, Fax { ... }  // 필요하면 조합
```

**왜 문제인가?**

- 쓰지 않는 메서드의 시그니처가 바뀌어도 해당 클라이언트가 **재컴파일/재배포**를 강요받는다
- 억지 구현이 늘면서 위의 `UnsupportedOperationException` 같은 LSP 위반으로 이어진다
- 테스트에서 Mock/Stub을 만들 때도 불필요한 메서드까지 신경 써야 한다

**분리 기준은 구현체가 아니라 클라이언트다.** "이 인터페이스를 쓰는 쪽이 어떤 메서드 집합을 필요로 하는가"를 기준으로 나눈다. SRP가 클래스(구현)의 책임 분리라면, ISP는 인터페이스(사용 계약)의 책임 분리다. 너무 잘게 쪼개 메서드 하나짜리 인터페이스가 난립하는 것도 경계해야 한다.

## DIP — 의존관계 역전 원칙

> 상위 모듈은 하위 모듈에 의존하면 안 된다. 둘 다 추상화에 의존해야 한다. 추상화는 세부사항에 의존하면 안 되고, 세부사항이 추상화에 의존해야 한다.

```text
[역전 전]
OrderService ───────────────▶ MySqlOrderRepository
(상위: 정책)                    (하위: 세부 구현)

[역전 후]
OrderService ──▶ OrderRepository (interface) ◀── MySqlOrderRepository
                 (추상화, 상위 모듈이 소유)
```

```java
// 위반: 도메인 로직이 구체 기술에 직접 의존
class OrderService {
    private final MySqlOrderRepository repository = new MySqlOrderRepository();
}

// 준수: 추상화에 의존, 구현체는 외부에서 주입
interface OrderRepository { void save(Order order); }

class OrderService {
    private final OrderRepository repository;

    OrderService(OrderRepository repository) {  // 생성자 주입
        this.repository = repository;
    }
}
```

"역전"이라는 이름의 핵심은 **의존 방향이 뒤집힌다**는 점이다. 원래는 상위 → 하위로 흐르던 소스 코드 의존성이, 추상화(인터페이스)를 사이에 두면서 하위 → 추상화 방향으로 바뀐다. 그리고 그 **인터페이스는 상위 모듈 쪽에 속한다**(상위 모듈의 요구에 맞춰 정의된다). 하위 모듈은 그 계약을 구현할 뿐이다.

**DIP vs IoC vs DI**

| 개념 | 정의 | 층위 |
|---|---|---|
| DIP | 추상화에 의존하라는 **설계 원칙** | 원칙 |
| IoC (제어의 역전) | 객체 생성·흐름의 제어권을 프레임워크/컨테이너가 가져가는 **개념** | 개념 |
| DI (의존성 주입) | 의존 객체를 외부에서 넣어주는 **구현 기법** | 기법 |

스프링 컨테이너가 DI를 해주는 것은 DIP를 지키기 쉽게 만들어 주는 도구일 뿐이다. 인터페이스 없이 구체 클래스를 주입받으면 DI는 쓰고 있어도 DIP는 지키지 못한 것이다.

**효과**: 구현체 교체가 쉽고(MySQL → PostgreSQL), 테스트에서 Fake/Mock으로 대체할 수 있으며, 도메인 로직이 인프라 변경에 흔들리지 않는다. 헥사고날/클린 아키텍처의 "의존성은 항상 안쪽(도메인)을 향한다"는 규칙이 DIP를 아키텍처 수준으로 확장한 것이다.

## 원칙 간의 관계

```text
SRP ── 변경 이유별로 모듈을 나눈다 ──▶ 응집도 ↑
ISP ── 사용 계약을 클라이언트별로 나눈다 ──▶ 불필요한 의존 ↓

OCP ── 확장은 추가로, 수정은 닫는다   (목표)
 ├─ LSP : 하위 타입이 상위 타입을 완벽히 대체해야 다형성이 성립  (전제)
 └─ DIP : 추상화에 의존해야 구현 추가가 가능                    (수단)
```

| 관점 | 원칙 |
|---|---|
| 책임을 어떻게 나누는가 | SRP, ISP |
| 변경에 어떻게 대응하는가 | OCP (목표), DIP (수단) |
| 다형성이 안전한가 | LSP |

## 적용 시 주의점

- **YAGNI/KISS와 충돌할 수 있다**: 변경이 일어나지 않을 코드에 인터페이스와 전략 클래스를 미리 만들면 이해 비용만 늘어난다. 구현체가 하나뿐인 인터페이스를 습관적으로 만드는 것이 대표적인 과설계다
- **변경이 실제로 발생한 지점에서 도입한다**: 같은 종류의 수정이 두세 번 반복될 때 추상화를 넣는 쪽이 비용 대비 효과가 좋다
- **SOLID는 코드 냄새를 진단하는 렌즈**다: 위반 자체가 버그는 아니다. 변경 시 고통이 있는지로 판단한다

| 위반 신호 (코드 냄새) | 의심되는 원칙 |
|---|---|
| 클래스 하나를 고치는데 관련 없는 테스트가 깨진다 | SRP |
| 기능 추가마다 `if/else`, `switch` 분기가 늘어난다 | OCP |
| `instanceof` 체크, `UnsupportedOperationException` | LSP |
| 빈 메서드/예외만 던지는 메서드를 억지로 구현한다 | ISP |
| 도메인 코드에서 `new 구체클래스()`, 인프라 import가 보인다 | DIP |

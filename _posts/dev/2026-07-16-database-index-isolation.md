## Summary

- 정규화는 데이터 중복과 이상현상(삽입·갱신·삭제 이상)을 없애는 과정이고, 반정규화는 그 대가로 늘어난 JOIN 비용을 성능을 위해 되돌리는 트레이드오프다
- SQL은 작성 순서(`SELECT` → `FROM` → ...)와 **논리적 실행 순서**(`FROM` → ... → `SELECT`)가 다르다 — `WHERE`에서 별칭(alias)을 못 쓰는 이유가 여기서 나온다
- 인덱스가 B+Tree인 이유는 **리프 노드가 연결 리스트로 이어져 있어 범위 검색(range scan)에 강하기** 때문이다 — 일반 B-Tree는 모든 노드에 데이터가 있어 정렬된 순회가 비효율적이다
- InnoDB는 PK 기준 **클러스터형 인덱스** 하나만 갖고, 나머지(세컨더리) 인덱스는 실제 행이 아니라 **PK 값을 가리킨다** — 그래서 PK가 크면 모든 세컨더리 인덱스가 커진다
- 인덱스 컬럼에 함수·연산을 적용하거나 앞부분에 와일드카드(`LIKE '%x'`)를 쓰면 인덱스를 타지 못한다 — 인덱스는 "정렬된 원본 값"을 기준으로 탐색하기 때문이다
- 격리 수준은 **정합성과 동시성의 트레이드오프**이며, MVCC는 락 없이도 이 트레이드오프의 균형점을 끌어올리는 기법이다 — 읽기가 쓰기를 막지 않는다

## 관계형 데이터베이스와 정규화

데이터베이스(Database)는 여러 사용자와 애플리케이션이 동시에 접근해도 정합성을 유지하며 데이터를 조직적으로 저장·조회·관리할 수 있게 해주는 시스템이다. 파일에 데이터를 직접 저장하는 방식과 달리, 동시성 제어·트랜잭션·질의 최적화·백업과 복구 같은 기능을 제공해 데이터의 정합성과 가용성을 보장한다.

관계형 데이터베이스(RDBMS)는 이 중에서도 데이터를 행과 열로 이루어진 **테이블**에 저장하고, 테이블 간 관계를 **외래키(FK)** 로 표현하는 방식이다.

### 정규화(Normalization)

데이터 중복을 줄이고 삽입·갱신·삭제 이상(anomaly)을 방지하기 위해 테이블을 분해하는 과정이다.

**정규화 전 — 하나의 테이블에 모든 정보가 뒤섞임**

| 주문번호 | 고객명 | 고객주소 | 상품명 | 상품가격 |
|---|---|---|---|---|
| 1 | 김철수 | 서울시 강남구 | 키보드 | 50000 |
| 2 | 김철수 | 서울시 강남구 | 마우스 | 20000 |

김철수가 이사하면 **모든 주문 행**의 주소를 다 고쳐야 한다(갱신 이상). 주문이 없는 고객은 아예 저장할 수 없다(삽입 이상). 김철수의 마지막 주문이 삭제되면 고객 정보 자체가 사라진다(삭제 이상).

**정규화 후 — 책임 단위로 테이블 분리**

```
고객(고객ID, 고객명, 고객주소)
상품(상품ID, 상품명, 상품가격)
주문(주문번호, 고객ID, 상품ID)
```

| 정규형 | 조건 |
|---|---|
| 1NF | 모든 컬럼이 원자값(atomic value)을 가진다 (하나의 셀에 여러 값 금지) |
| 2NF | 1NF + 기본키의 **일부**에만 종속되는 컬럼(부분 함수 종속) 제거 |
| 3NF | 2NF + 기본키가 아닌 컬럼이 다른 일반 컬럼에 종속되는 것(이행 함수 종속) 제거 |

**왜 필요한가?** 고객 주소가 바뀌어도 `고객` 테이블 한 행만 고치면 되고, 주문이 없어도 고객을 저장할 수 있으며, 주문을 지워도 고객 정보는 남는다. 정규화는 각 테이블이 "하나의 사실"만 책임지게 만드는 것이다.

**반정규화(Denormalization)**

정규화된 구조는 조회할 때마다 여러 테이블을 JOIN해야 해서 읽기 성능이 떨어질 수 있다. 조회가 압도적으로 많고 갱신은 드문 경우, 의도적으로 중복 컬럼을 추가하거나 테이블을 합쳐 JOIN을 줄이는 것이 반정규화다. 예를 들어 `주문` 테이블에 `상품명`을 중복 저장해두면 상품명 조회 시 JOIN 없이 바로 읽을 수 있지만, 상품명이 바뀌면 여러 곳을 동기화해야 하는 대가를 진다. **정합성(정규화) vs 조회 성능(반정규화)** 트레이드오프다.

## 트랜잭션과 ACID

트랜잭션은 더 이상 쪼갤 수 없는 하나의 작업 단위다. "계좌 A에서 출금 + 계좌 B에 입금"처럼 여러 연산이 모두 성공하거나 모두 실패해야 하는 묶음을 표현한다.

| 속성 | 의미 |
|---|---|
| **원자성(Atomicity)** | 트랜잭션 내 연산은 전부 성공하거나 전부 실패한다(All or Nothing) |
| **일관성(Consistency)** | 트랜잭션 전후로 데이터베이스는 정의된 제약(무결성 규칙)을 항상 만족한다 |
| **격리성(Isolation)** | 동시에 실행되는 트랜잭션들은 서로 영향을 주지 않는다 (아래 섹션에서 상세히 다룸) |
| **지속성(Durability)** | 커밋된 트랜잭션의 결과는 시스템 장애가 나도 영구적으로 보존된다 |

**원자성은 어떻게 보장되는가?** 트랜잭션 도중 장애가 나면 **롤백(rollback)** 으로 실행 이전 상태로 되돌린다. RDBMS는 변경 사항을 실제 데이터 파일에 반영하기 전, 그 변경 내역을 별도의 로그(예: MySQL InnoDB의 undo log)에 먼저 기록해두고, 실패 시 이 로그를 거꾸로 적용해 원상복구한다.

**지속성은 어떻게 보장되는가?** 커밋 시점에 변경 내용을 로그(redo log)에 먼저 기록(Write-Ahead Logging)한 뒤 커밋을 완료 처리한다. 커밋 직후 서버가 죽어도, 재시작 시 이 로그를 재생(replay)해 커밋된 변경을 복구할 수 있다.

## SQL 실행 순서와 조인

### 논리적 실행 순서

SQL은 **작성 순서**와 **논리적 실행 순서**가 다르다.

```sql
SELECT   department, COUNT(*) AS cnt
FROM     employee
WHERE    salary > 3000
GROUP BY department
HAVING   COUNT(*) > 2
ORDER BY cnt DESC
LIMIT    10;
```

| 실행 순서 | 절 |
|:--:|---|
| 1 | `FROM` (+ `JOIN`) |
| 2 | `WHERE` |
| 3 | `GROUP BY` |
| 4 | `HAVING` |
| 5 | `SELECT` |
| 6 | `ORDER BY` |
| 7 | `LIMIT` |

**왜 `WHERE`에서 `SELECT`의 별칭(alias)을 쓸 수 없는가?** `WHERE`는 `SELECT`보다 먼저 실행되므로, `WHERE` 실행 시점에는 `cnt`라는 별칭이 아직 존재하지 않는다(`WHERE cnt > 2`는 오류). 반면 `HAVING`은 `SELECT`보다 뒤에 실행되는 DB도 있어 별칭을 허용하는 경우가 있지만, 표준적으로는 `GROUP BY` 결과(집계값) 자체를 다루므로 집계 함수를 다시 써야 한다.

### JOIN 종류

| 종류 | 결과 |
|---|---|
| `INNER JOIN` | 양쪽 테이블에 모두 매칭되는 행만 |
| `LEFT JOIN` | 왼쪽 테이블 전체 + 매칭되는 오른쪽 행(없으면 NULL) |
| `RIGHT JOIN` | 오른쪽 테이블 전체 + 매칭되는 왼쪽 행(없으면 NULL) |
| `FULL OUTER JOIN` | 양쪽 전체(매칭 안 되는 행도 NULL로 채워 포함) |
| `CROSS JOIN` | 두 테이블의 모든 행 조합(카티션 곱) |

### JOIN 알고리즘

옵티마이저가 테이블 크기·인덱스 유무에 따라 선택한다.

- **Nested Loop Join**: 바깥 테이블의 각 행마다 안쪽 테이블을 순회하며 매칭. 안쪽 테이블 조인 컬럼에 인덱스가 있으면 매우 효율적이지만, 없으면 O(N×M)으로 느려진다.
- **Hash Join**: 작은 쪽 테이블로 해시 테이블을 만들고, 큰 쪽 테이블을 순회하며 해시로 매칭. 인덱스가 없어도 상대적으로 빠르지만 해시 테이블을 메모리에 올려야 한다.
- **Sort Merge Join**: 양쪽 테이블을 조인 컬럼 기준으로 정렬한 뒤, 정렬된 두 리스트를 동시에 순회하며 병합. 이미 정렬되어 있거나(인덱스로 정렬 보장) 등가 조인이 아닐 때 유리하다.

## 인덱스(Index)

인덱스는 테이블 전체를 스캔(Full Table Scan)하지 않고도 원하는 행을 빠르게 찾기 위해 특정 컬럼 값을 **정렬된 별도 자료구조**로 미리 만들어둔 것이다. 책의 "찾아보기"와 같은 개념이다.

### 왜 B+Tree인가?

일반 이진 탐색 트리(BST)는 삽입 순서에 따라 한쪽으로 치우쳐(skewed) 퇴화할 수 있어, DB 인덱스는 스스로 균형을 잡는 **B-Tree 계열**을 쓴다. 그중에서도 대부분의 RDBMS(MySQL InnoDB 등)는 **B+Tree**를 쓴다.


| 구분 | B-Tree | B+Tree |
|---|---|---|
| 데이터 저장 위치 | 모든 노드(내부 노드 포함) | **리프 노드에만** |
| 내부 노드 역할 | 데이터 + 라우팅 | 라우팅(인덱싱)만 |
| 리프 노드 간 연결 | 없음 | **연결 리스트로 연결** |
| Range Scan | 트리를 오르내리며 순회 필요 | 리프 노드 연결 리스트만 따라가면 됨 |

**왜 필요한가?** `WHERE age BETWEEN 20 AND 30`처럼 범위 검색을 할 때, B+Tree는 시작점 하나만 트리 탐색으로 찾고 그 뒤로는 리프 노드의 연결 리스트를 순서대로 읽기만 하면 된다. B-Tree는 내부 노드에도 데이터가 흩어져 있어 범위 전체를 순회하려면 트리를 오르내려야 한다. 또한 B+Tree는 내부 노드가 라우팅 정보만 가지므로(실제 데이터가 없어 더 작음) 하나의 노드(디스크 페이지)에 더 많은 키를 담을 수 있어 트리 높이가 낮아지고, 그만큼 디스크 I/O 횟수가 줄어든다.

### 왜 해시 인덱스가 아니라 B+Tree인가

등치 비교(`=`)만 따지면 해시 테이블이 평균 O(1)로 B+Tree(O(log n))보다 이론적으로 더 빠르다. 그런데도 대부분의 RDBMS가 범용 인덱스로 B+Tree를 기본으로 쓰는 이유는 해시 테이블이 키를 해시값으로 흩어 저장해 **정렬 순서를 보존하지 않기** 때문이다. 범위 검색(`BETWEEN`, `>`, `<`)이나 정렬(`ORDER BY`), 접두어 검색(`LIKE 'kim%'`)은 정렬된 순서를 전제로 동작하는데, 해시 인덱스로는 이런 질의를 원리상 지원할 수 없어 결국 풀스캔으로 빠져야 한다. 실무 쿼리는 등치 비교뿐 아니라 범위 조건·정렬을 함께 요구하는 경우가 많아, 범용 인덱스는 B+Tree를 기본으로 쓰고 해시 인덱스는 등치 비교만 확실한 특수한 경우(PostgreSQL의 `HASH` 인덱스 등)에 선택적으로 제공한다.

### 클러스터형 인덱스 vs 논클러스터형 인덱스

| 구분 | 클러스터형(Clustered) | 논클러스터형(Non-clustered, Secondary) |
|---|---|---|
| 데이터 물리적 정렬 | 인덱스 순서 = 데이터 저장 순서 | 별도 자료구조, 데이터 순서와 무관 |
| 테이블당 개수 | 1개(InnoDB는 PK 기준) | 여러 개 가능 |
| 리프 노드 내용 | **실제 행 데이터 전체** | PK 값(InnoDB) 또는 행 포인터 |

InnoDB는 PK를 기준으로 클러스터형 인덱스를 만든다. 세컨더리 인덱스의 리프 노드는 실제 데이터가 아니라 **PK 값**을 가리키므로, 세컨더리 인덱스로 검색하면 ① 세컨더리 인덱스에서 PK를 찾고 → ② 그 PK로 클러스터형 인덱스를 다시 탐색해 실제 행을 가져오는 **두 번의 탐색(bookmark lookup)** 이 일어난다.

**PK가 없으면 어떻게 되는가?** PK가 없으면 `NOT NULL UNIQUE` 제약을 가진 컬럼을 대신 클러스터 키로 쓰고, 그마저도 없으면 InnoDB가 내부적으로 숨겨진 6바이트 `ROW_ID`를 자동 생성해 클러스터 키로 사용한다. 이 경우 애플리케이션에서 직접 접근할 수 없는 값이라 사실상 관리 밖의 클러스터형 인덱스가 만들어지는 셈이라, 명시적으로 PK를 정의하는 것이 권장된다.

**왜 PK가 크면 안 좋은가?** 모든 세컨더리 인덱스의 리프 노드가 PK 값을 들고 있으므로, PK 타입이 크면(예: `UUID` 문자열) 세컨더리 인덱스가 하나 늘 때마다 그만큼 저장 공간이 배가된다. 그래서 InnoDB에서는 auto-increment 정수형 PK를 권장한다.

**"프라이머리 인덱스"와 "세컨더리 인덱스"는 클러스터형/논클러스터형과 같은 말인가?** 데이터베이스 이론에서 프라이머리 인덱스는 "데이터의 물리적 정렬 기준이 되는 인덱스", 세컨더리 인덱스는 "그 정렬과 무관하게 별도로 만든 인덱스"를 가리키는 좀 더 일반적인 용어다. InnoDB처럼 PK 기준으로 데이터를 물리적으로 정렬해 저장하는 클러스터형 구조에서는 프라이머리 인덱스가 곧 클러스터형 인덱스와 사실상 같은 의미로, 세컨더리 인덱스도 논클러스터형과 같은 의미로 쓰인다. 다만 클러스터형 인덱스를 지원하지 않고 데이터를 힙(heap) 구조로 저장하는 DB(PostgreSQL의 기본 테이블 등)에서는 프라이머리 인덱스도 논클러스터형처럼 별도 자료구조로 존재해, 두 용어가 항상 1:1로 대응하지는 않는다.

**그럼에도 UUID를 PK로 쓰는 경우** 저장 공간 비용에도 불구하고, 여러 서버·클라이언트가 중앙 조정 없이 동시에 고유한 값을 생성해야 하는 분산 환경에서는 UUID가 선호되기도 한다. auto-increment는 값을 채번하는 주체(DB 서버)가 하나여야 순서와 유일성이 보장되는데, 여러 인스턴스가 동시에 레코드를 만드는 구조에서는 이 채번 자체가 병목이나 충돌 조정 지점이 될 수 있기 때문이다. 저장 공간과 인덱스 지역성(locality) 문제를 줄이면서도 이런 이점을 살리려는 절충안으로, 시간 순서를 접두어에 인코딩해 정렬 가능하게 만든 UUIDv7이나 ULID 같은 대안도 쓰인다.

### 커버링 인덱스(Covering Index)

쿼리에서 필요한 모든 컬럼이 인덱스 자체에 포함되어 있어, 실제 테이블(클러스터형 인덱스)까지 갈 필요 없이 인덱스만으로 결과를 반환할 수 있는 경우다.

```sql
CREATE INDEX idx_name_age ON employee (name, age);

SELECT name, age FROM employee WHERE name = 'kim';
-- idx_name_age 인덱스만 읽으면 name, age 둘 다 있어 테이블 접근(bookmark lookup) 불필요
```

### 복합 인덱스와 컬럼 순서

여러 컬럼으로 인덱스를 만들 때, **컬럼 순서**가 성능을 좌우한다.

```sql
CREATE INDEX idx_a_b ON t (col_a, col_b);
```

- `WHERE col_a = 1 AND col_b = 2` → 인덱스 사용 O
- `WHERE col_a = 1` → 인덱스 사용 O (선두 컬럼만 조건에 있어도 됨)
- `WHERE col_b = 2` → 인덱스 사용 X (**leftmost prefix rule** — 왼쪽부터 순서대로 조건에 있어야 인덱스를 탈 수 있다. 선두 컬럼이 빠지면 인덱스를 탈 수 없다)

**컬럼 순서를 정하는 기준 — 카디널리티(Cardinality)와 선택도(Selectivity)**: 카디널리티는 컬럼이 가질 수 있는 값의 **종류 수**를 말한다(예: `성별`은 카디널리티 2, `주민번호`는 거의 행 수만큼 카디널리티가 높다). 선택도는 이 카디널리티를 바탕으로 "조건 하나로 걸러지는 행의 비율"을 뜻하며, 카디널리티가 높을수록 선택도도 높아진다. 일반적으로 **선택도가 높은(카디널리티가 높은) 컬럼을 앞에** 두면 앞 단계에서 후보군이 크게 좁혀져 효율적이다. 단, `WHERE`와 `ORDER BY`를 함께 최적화해야 한다면 등치(`=`) 조건 컬럼을 범위(`BETWEEN`, `>`) 조건 컬럼보다 앞에 두는 것이 우선이다 — 범위 조건 이후의 컬럼은 정렬 순서가 깨져 인덱스를 활용하지 못하기 때문이다.

### 인덱스를 타지 못하는 경우

- 인덱스 컬럼에 **함수나 연산을 적용**한 경우: `WHERE YEAR(created_at) = 2026`, `WHERE price * 1.1 > 1000` — 인덱스는 원본 값 기준으로 정렬되어 있으므로, 컬럼을 가공하면 그 정렬을 활용할 수 없다.
- **앞부분에 와일드카드**가 있는 `LIKE`: `LIKE '%kim'`은 인덱스 사용 불가, `LIKE 'kim%'`은 사용 가능. 인덱스는 문자열을 앞에서부터 정렬해두므로, 뒷부분이 고정된 검색은 어디서 시작해야 할지 알 수 없다.
- **타입이 불일치**하는 비교: 문자열 컬럼에 숫자를 비교하면(`WHERE phone = 01012345678`) 암묵적 형변환이 일어나 인덱스를 못 타는 경우가 있다.
- `OR`로 연결된 조건 중 일부 컬럼에 인덱스가 없으면 전체가 풀스캔될 수 있다.
- `NOT IN`, `<>`, `IS NOT NULL`처럼 "아닌 것"을 찾는 조건은 인덱스로 좁힐 수 있는 범위가 작아 옵티마이저가 풀스캔을 택하기도 한다.

### 인덱스의 비용

인덱스는 읽기(`SELECT`)를 빠르게 하는 대신, `INSERT`/`UPDATE`/`DELETE` 시마다 인덱스 자료구조도 함께 갱신해야 해서 **쓰기 성능이 떨어지고 저장 공간을 추가로 차지**한다. 그래서 조회 패턴을 분석해 실제로 자주 쓰이는 컬럼에만 선택적으로 인덱스를 만들어야 한다.

**옵티마이저가 인덱스를 두고도 안 타는 경우**: 조건에 맞는 행이 전체 테이블의 상당 비율(예: 20~30% 이상)을 차지하면, 세컨더리 인덱스로 건마다 bookmark lookup을 반복하는 비용이 그냥 Full Table Scan보다 커진다고 옵티마이저가 판단해 인덱스를 무시하고 풀스캔을 택하기도 한다. "인덱스가 있는데 왜 안 타나요?"라는 질문의 답은 대개 이 비용 기반 판단이다.

### 실행계획(EXPLAIN) 읽는 법

`EXPLAIN SELECT ...`로 옵티마이저가 실제로 어떻게 실행할지 미리 확인할 수 있다. MySQL 기준 주요 컬럼:

| 컬럼 | 의미 |
|---|---|
| `type` | 접근 방식. `const`/`eq_ref`(최상) → `ref` → `range` → `index` → `ALL`(풀스캔, 최악) 순으로 나쁨 |
| `key` | 실제로 선택된 인덱스. `NULL`이면 인덱스를 못 탄 것 |
| `rows` | 옵티마이저가 예상하는 검사 대상 행 수 — 작을수록 좋음 |
| `Extra` | 부가 정보. `Using filesort`(추가 정렬 필요), `Using temporary`(임시 테이블 사용) 등이 뜨면 최적화 여지가 있다는 신호 |

`type`이 `ALL`이거나 `key`가 `NULL`이면 의도한 인덱스를 못 타고 있다는 뜻이므로 쿼리나 인덱스 설계를 다시 봐야 한다.

## 트랜잭션 격리 수준(Isolation Level)

### 격리성 위반 시 발생하는 문제

#### Dirty Read

커밋되지 않은 데이터를 다른 트랜잭션이 읽는 현상이다.

| 시간 | 트랜잭션 A | 트랜잭션 B |
|:--:|---|---|
| T1 | `balance = 1000 → 2000` (미커밋) | |
| T2 | | `balance` 읽음 → **2000** |
| T3 | ROLLBACK | |
| T4 | | 2000을 기준으로 작업 진행 → **잘못된 데이터** |

A가 롤백했지만 B는 이미 존재하지 않는 값을 기준으로 동작했다.

#### Non-repeatable Read

같은 트랜잭션 내에서 같은 행을 두 번 읽었을 때 결과가 달라지는 현상이다.

| 시간 | 트랜잭션 A | 트랜잭션 B |
|:--:|---|---|
| T1 | `balance` 읽음 → **1000** | |
| T2 | | `balance = 2000` UPDATE + COMMIT |
| T3 | `balance` 다시 읽음 → **2000** | |

같은 트랜잭션 안에서 읽은 값이 달라졌다.

#### Phantom Read

같은 트랜잭션 내에서 같은 조건으로 조회했을 때 행의 **개수**가 달라지는 현상이다.

| 시간 | 트랜잭션 A | 트랜잭션 B |
|:--:|---|---|
| T1 | `age > 20` 조회 → **3건** | |
| T2 | | 새 행 INSERT + COMMIT |
| T3 | `age > 20` 다시 조회 → **4건** | |

Non-repeatable Read가 기존 행의 **값** 변경이라면, Phantom Read는 행의 **추가/삭제**로 인한 문제다.

### 트랜잭션 격리 수준

#### READ UNCOMMITTED

커밋되지 않은 변경 사항도 읽을 수 있다.

- 세 가지 문제 모두 발생
- 사실상 격리성 없음
- 실무에서 거의 사용하지 않는다

#### READ COMMITTED

커밋된 데이터만 읽는다. 대부분의 RDBMS 기본값이다. (PostgreSQL, Oracle 등)

- Dirty Read 방지
- Non-repeatable Read, Phantom Read 발생 가능

#### REPEATABLE READ

트랜잭션 시작 시점의 스냅샷을 기준으로 읽는다. MySQL InnoDB 기본값이다.

- Dirty Read, Non-repeatable Read 방지
- Phantom Read 발생 가능 (단, MySQL InnoDB는 MVCC로 Phantom Read도 대부분 방지)

#### SERIALIZABLE

트랜잭션을 순차 실행한 것과 동일한 결과를 보장한다.

- 세 가지 문제 모두 방지
- 읽기에도 공유 잠금이 걸려 동시성이 크게 저하된다
- 데이터 정합성이 가장 중요한 경우에만 사용

### 격리 수준별 문제 발생 여부

| 격리 수준 | Dirty Read | Non-repeatable Read | Phantom Read |
|:--:|:--:|:--:|:--:|
| READ UNCOMMITTED | 발생 | 발생 | 발생 |
| READ COMMITTED | 방지 | 발생 | 발생 |
| REPEATABLE READ | 방지 | 방지 | 발생 |
| SERIALIZABLE | 방지 | 방지 | 방지 |

### DBMS별 기본 격리 수준

| DBMS | 기본 격리 수준 |
|---|---|
| MySQL (InnoDB) | REPEATABLE READ |
| PostgreSQL | READ COMMITTED |
| Oracle | READ COMMITTED |
| SQL Server | READ COMMITTED |

표준 SQL이 권장하는 기본값은 READ COMMITTED이고, 대부분의 RDBMS가 이를 따른다 — MySQL InnoDB의 REPEATABLE READ 기본값이 오히려 예외적인 편이다. 다만 이름이 같다고 동작까지 같은 건 아니다. PostgreSQL의 REPEATABLE READ는 트랜잭션 시작 시점의 스냅샷을 고정해서 읽는 것을 넘어, 쓰기 충돌까지 감지해 한쪽을 실패시키는 **스냅샷 격리(Snapshot Isolation)**로 구현되어 있어 MySQL InnoDB의 REPEATABLE READ보다 더 강한 보장을 제공한다.

**왜 전부 SERIALIZABLE로 쓰지 않는가?** SERIALIZABLE은 읽기에도 잠금이 걸려 사실상 트랜잭션을 순차 실행하는 것과 비슷하게 동작하므로, 동시에 처리할 수 있는 트랜잭션 수가 크게 줄고 락 대기·데드락 가능성도 늘어난다. 대부분의 애플리케이션은 이상현상이 발생할 가능성이 낮거나 발생해도 감내할 수 있는 반면 처리량 저하는 즉시 체감되는 비용이라, 회계 정산처럼 정합성이 절대적으로 중요한 일부 트랜잭션에만 선택적으로 사용한다.

### MVCC(Multi-Version Concurrency Control)

읽기 작업에 락을 걸지 않고도 일관된 스냅샷을 제공하는 기법이다. 각 행이 변경될 때마다 이전 버전을 **undo log**에 보관해두고, 트랜잭션은 자신의 스냅샷 기준 시점에 "그 시점에 유효했던 버전"을 읽는다.

**왜 필요한가?** 락 기반으로만 격리성을 구현하면 읽기와 쓰기가 서로를 블로킹해 동시성이 크게 떨어진다. MVCC는 **쓰기가 읽기를 막지 않고, 읽기가 쓰기를 막지 않도록** 해 락 경합 없이 일관성을 제공한다.

**스냅샷 기준 시점이 격리 수준마다 다르다** — 이 차이가 곧 READ COMMITTED와 REPEATABLE READ의 실제 동작 차이다.

- **READ COMMITTED**: 매 `SELECT` 문(statement)마다 그 시점 기준으로 새 스냅샷을 뜬다. 그래서 같은 트랜잭션 안에서도 두 번째 `SELECT`는 그 사이 커밋된 변경을 반영한 새 스냅샷을 보게 되어 Non-repeatable Read가 발생한다.
- **REPEATABLE READ**: 트랜잭션이 시작된 시점(정확히는 트랜잭션의 첫 조회 시점)에 스냅샷을 한 번 고정하고, 트랜잭션이 끝날 때까지 계속 같은 스냅샷을 읽는다. 그래서 트랜잭션 도중 다른 트랜잭션이 커밋해도 값이 바뀌어 보이지 않아 Non-repeatable Read가 방지된다.

### 잠금(Lock)의 종류

MVCC로 읽기 일관성은 해결되지만, 쓰기 충돌(두 트랜잭션이 같은 행을 동시에 수정)은 여전히 락으로 제어해야 한다.

| 락 종류 | 설명 |
|---|---|
| 공유 락(Shared Lock, S) | 읽기 락. 다른 트랜잭션의 공유 락과는 공존 가능, 배타 락과는 불가 |
| 배타 락(Exclusive Lock, X) | 쓰기 락. 다른 어떤 락과도 공존 불가 |

**InnoDB의 REPEATABLE READ에서 Phantom Read 방지 메커니즘 — Gap Lock / Next-Key Lock**

일반적인 REPEATABLE READ는 이론상 Phantom Read를 막지 못하지만, InnoDB는 **Next-Key Lock**(레코드 락 + 갭 락)으로 이를 상당 부분 방지한다. **갭 락(Gap Lock)**은 인덱스 레코드 "사이의 간격"에 거는 락으로, 그 범위에 새로운 행이 INSERT되는 것 자체를 막는다. 예를 들어 `WHERE age BETWEEN 20 AND 30 FOR UPDATE`를 실행하면, 기존 행뿐 아니라 그 범위 안의 "빈 공간"에도 락이 걸려 다른 트랜잭션이 `age = 25`인 새 행을 끼워 넣을 수 없다.

**심화 — Consistent Read와 Locking Read의 차이** 그렇다고 Phantom Read가 원천적으로 불가능해지는 것은 아니다. 일반 `SELECT`(Consistent Non-locking Read)는 트랜잭션의 첫 조회 시점에 고정한 스냅샷만 보므로 애초에 새 행이 눈에 보이지 않는다. 반면 `SELECT ... FOR UPDATE`, `UPDATE`, `DELETE`처럼 최신 커밋 데이터를 대상으로 하는 Locking(Current) Read는 스냅샷이 아니라 실행 시점의 최신 상태를 보고, 그 순간 Next-Key Lock으로 이후의 INSERT만 차단한다. 그래서 같은 트랜잭션 안에서 일반 `SELECT`로 3건을 확인한 뒤 곧바로 같은 조건으로 `UPDATE`를 실행하면, 그 사이 다른 트랜잭션이 커밋한 새 행까지 갱신 대상에 포함될 수 있다 — "조회한 것"과 "실제로 잠그거나 변경하는 대상"이 다를 수 있다는 InnoDB REPEATABLE READ의 실무적인 함정이다.

### Lost Update와 낙관적 락 / 비관적 락

**Lost Update(갱신 손실)**: 두 트랜잭션이 같은 행을 동시에 읽고, 각자 계산한 값으로 덮어쓰면 먼저 쓴 트랜잭션의 변경이 사라지는 현상이다.

| | 비관적 락(Pessimistic Lock) | 낙관적 락(Optimistic Lock) |
|---|---|---|
| 전제 | 충돌이 자주 일어날 것이라 가정 | 충돌이 드물 것이라 가정 |
| 구현 | `SELECT ... FOR UPDATE`로 배타 락을 걸어, 읽는 시점부터 다른 트랜잭션의 접근 자체를 막음 | 실제 락을 걸지 않고, 행에 `version` 컬럼을 두어 `UPDATE ... WHERE id = ? AND version = ?`처럼 갱신 시점에 버전이 그대로인지 확인 |
| 충돌 시 동작 | 락이 풀릴 때까지 다른 트랜잭션이 대기 | `UPDATE`의 영향 행 수가 0이면(버전 불일치) 애플리케이션이 충돌을 감지해 재시도하거나 예외 처리 |
| 트레이드오프 | 대기로 인한 처리량 저하, 데드락 위험 | 락 오버헤드는 없지만 충돌이 잦으면 재시도 비용이 커짐 |

**언제 무엇을 쓰는가?** 동시 수정이 잦고 반드시 순서를 보장해야 하는 경우(재고 차감, 좌석 예약)는 비관적 락이 안전하다. 조회는 많고 실제 충돌은 드문 경우(게시글 조회수, 프로필 수정)는 낙관적 락이 락 대기 없이 처리량을 높일 수 있다.

### Deadlock(교착 상태)

두 트랜잭션이 서로 상대가 가진 락을 기다리며 영원히 블로킹되는 상황이다. 예를 들어 트랜잭션 A가 행 1의 락을 쥔 채 행 2를 기다리고, 트랜잭션 B가 행 2의 락을 쥔 채 행 1을 기다리면 둘 다 영원히 대기한다.

- **감지(Detection)**: RDBMS는 락 대기 그래프를 감시하다 순환(cycle)을 감지하면 그중 처리 비용이 더 적은 트랜잭션을 강제로 롤백시켜 해소한다.
- **예방(Prevention)**:
  - 여러 트랜잭션이 여러 행을 잠글 때 **항상 같은 순서**로 잠그도록 애플리케이션 로직을 통일하면(예: 항상 PK 오름차순으로 접근) 순환 대기 자체가 만들어지지 않는다.
  - `lock_wait_timeout` 같은 락 대기 타임아웃을 설정해, 일정 시간 이상 대기하면 감지를 기다리지 않고 스스로 실패 처리하도록 한다.
  - 트랜잭션을 짧게 유지하고 락을 거는 범위를 최소화하면 충돌 가능성 자체가 줄어든다.

### JPA / Spring에서 격리 수준 지정

JPA 표준 자체에는 격리 수준을 지정하는 API가 없다. 별도로 설정하지 않으면 커넥션 풀이 맺은 JDBC 커넥션의 기본 격리 수준, 즉 DB 서버의 기본값을 그대로 따른다. Spring을 함께 쓰는 경우 `@Transactional(isolation = Isolation.READ_COMMITTED)`처럼 트랜잭션 시작 전에 `Connection.setTransactionIsolation()`을 호출해 그 트랜잭션에 한해 격리 수준을 재정의할 수 있다.

**주의할 점** 커넥션 풀은 커넥션을 재사용하므로, 트랜잭션이 끝나면 원래 격리 수준으로 복원해야 다음 요청이 의도치 않은 격리 수준으로 실행되는 걸 막을 수 있다(대부분의 트랜잭션 매니저가 이를 자동으로 처리한다). 또한 일부 DBMS·드라이버는 트랜잭션 도중 격리 수준 변경을 허용하지 않거나 이미 시작된 트랜잭션에는 적용하지 않으므로, 반드시 트랜잭션 시작 전에 설정해야 한다.

### MySQL과 PostgreSQL, 무엇이 다른가

같은 오픈소스 RDBMS라도 설계 철학이 다르다. MySQL은 단순하고 빠른 처리에 최적화된 반면, PostgreSQL은 SQL 표준 준수도와 확장성에 무게를 둔다.

| 항목 | MySQL (InnoDB) | PostgreSQL |
|---|---|---|
| 기본 격리 수준 | REPEATABLE READ | READ COMMITTED |
| MVCC 저장 방식 | Undo Log에 이전 버전 보관 | 튜플 자체에 여러 버전을 직접 보관(구버전은 VACUUM으로 정리) |
| 데이터 타입 | 비교적 단순 | 배열, JSONB, 사용자 정의 타입 등 풍부 |
| 확장성 | 플러그인형 스토리지 엔진 | `PostGIS`, `pg_trgm` 등 확장(extension) 생태계 |
| SQL 표준 준수 | 부분적 준수, 일부 독자 문법 | 표준에 더 가깝게 구현 |

정형화된 스키마로 단순 CRUD 위주의 서비스를 빠르게 만들 때는 MySQL이, 복잡한 쿼리·풍부한 데이터 타입·표준 준수가 중요한 서비스에는 PostgreSQL이 더 널리 선택되는 편이다.

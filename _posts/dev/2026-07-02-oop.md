## Summary

- OOP의 4대 특성(캡슐화·상속·다형성·추상화)은 독립된 개념이 아니라 서로 맞물려 작동한다 — "왜" 그 특성이 필요한가를 알아야 실무에서 쓸 수 있다
- 캡슐화는 "필드를 숨긴다"가 아니라 "객체가 스스로 유효한 상태(불변식)를 지킨다"는 것까지 포함한다 — 무분별한 getter/setter는 이 보호를 무력화한다
- 인터페이스와 추상 클래스는 용도가 다르다 — 인터페이스는 "무엇을 할 수 있는가(능력)", 추상 클래스는 "무엇인가(정체성)"
- 상속은 IS-A 관계에서만 쓰고, 그 외에는 조합(Composition)을 선택해야 상위 클래스 구현 변경에 깨지지 않는다
- `equals()`와 `hashCode()`는 항상 함께 오버라이딩해야 한다 — HashMap/HashSet의 탐색 메커니즘이 두 메서드를 모두 사용하기 때문이다
- 오버라이딩 시 접근 제어자는 좁힐 수 없고 반환 타입은 좁힐 수 있는(공변 반환 타입) 정반대 규칙은 둘 다 리스코프 치환 원칙(LSP)에서 나온다 — 호출자와의 계약을 깨지 않아야 한다는 하나의 기준
- 불변 객체는 생성 이후 "쓰기"라는 이벤트 자체가 없어 별도 동기화 없이도 스레드 안전하다
- SOLID는 다형성·조합·응집도 같은 OOP 개념을 실무 설계 기준으로 구체화한 것이다

## 4대 특성

### 캡슐화 (Encapsulation)

데이터(필드)와 그 데이터를 다루는 동작(메서드)을 하나의 단위로 묶고, 외부에서 내부 상태에 직접 접근하지 못하도록 **은닉**하는 것이다.

```java
public class BankAccount {
    private long balance;  // 외부 직접 접근 차단

    public void deposit(long amount) {
        if (amount <= 0) throw new IllegalArgumentException();
        balance += amount;
    }

    public long getBalance() {
        return balance;
    }
}
```

접근 제어자 범위:

| 접근 제어자 | 같은 클래스 | 같은 패키지 | 하위 클래스 | 전체 |
|---|:---:|:---:|:---:|:---:|
| `private` | O | X | X | X |
| `(default)` | O | O | X | X |
| `protected` | O | O | O | X |
| `public` | O | O | O | O |

**왜 필요한가?** 내부 구현이 바뀌어도 외부 코드가 영향을 받지 않는다. `balance` 타입을 `int`에서 `long`으로 바꿔도, 외부는 `getBalance()`만 호출하므로 변경 전파가 차단된다.

**캡슐화 = 은닉 + 불변식(invariant) 보호**

캡슐화를 "필드를 `private`으로 감추는 것"으로만 이해하면 놓치는 지점이 있다. 모든 필드에 getter/setter를 무조건 열어두는 클래스는 필드를 감춘 것처럼 보이지만, 실질적으로는 `public` 필드와 다를 게 없다.

```java
// 캡슐화를 지킨 것처럼 보이지만 사실상 무방비
public class BankAccount {
    private long balance;
    public void setBalance(long balance) { this.balance = balance; }  // 위험!
    public long getBalance() { return balance; }
}

account.setBalance(-1000);  // "잔고는 음수가 될 수 없다"는 규칙을 통째로 우회
```

`setBalance()`는 어떤 값이든 그대로 대입할 수 있게 허용하므로, 객체가 항상 유효한 상태를 유지해야 한다는 불변식이 무분별하게 깨질 수 있다. 대신 `deposit()`/`withdraw()`처럼 의미 있는 동작 단위로 메서드를 노출하면, 그 메서드 내부에서 검증 로직을 강제할 수 있어 객체가 항상 유효한 상태를 유지한다. 즉 캡슐화는 "데이터 은닉"을 넘어 "불변식 보호"까지 의미한다.

### 상속 (Inheritance)

부모 클래스의 필드와 메서드를 자식 클래스가 물려받아 재사용하는 메커니즘이다. IS-A 관계에서만 쓰는 것이 원칙이다.

```java
public class Animal {
    protected String name;

    public void eat() { System.out.println(name + " is eating"); }
}

public class Dog extends Animal {
    public void bark() { System.out.println("Woof!"); }
}
```

**생성자 체인**: 자식 객체 생성 시 부모 생성자가 먼저 호출된다. 자식 생성자 첫 줄에 `super()`가 명시되지 않으면 컴파일러가 인수 없는 `super()`를 자동 삽입한다. 부모 클래스에 매개변수 없는 생성자가 없다면 "일치하는 생성자를 찾을 수 없다"는 컴파일 에러가 난다.

**메서드 오버라이딩 규칙**:
- 접근 제어자는 부모보다 좁힐 수 없다 (public → private 불가)
- 반환 타입은 부모 반환 타입의 하위 타입(공변 반환 타입)을 허용한다
- 체크 예외는 부모보다 넓은 예외를 던질 수 없다

**왜 접근 제어자와 반환 타입은 정반대 방향의 규칙을 가질까?**

세 규칙 모두 **리스코프 치환 원칙(LSP)** — "부모 타입으로 작성된 호출 코드가 자식 객체로 바뀌어도 깨지지 않아야 한다" — 에서 나온다.

- 접근 제어자를 좁히면(`public` → `private`), 부모 타입 참조로 호출하려던 코드가 컴파일조차 되지 않으므로 계약 위반이다. 그래서 금지된다.
- 반환 타입을 좁히는 것(예: `Animal` 대신 `Dog` 반환)은 "적어도 `Animal`"이라는 약속을 어기지 않는다. `Dog`는 `Animal`이기도 하므로 호출자 입장에서는 오히려 상위 호환이다. 그래서 허용된다(공변 반환 타입).
- 체크 예외도 마찬가지다. 부모가 특정 예외만 던진다고 계약했는데 자식이 더 넓은 예외를 던지면, 그 예외를 모르고 작성된 호출자의 `catch` 블록이 처리하지 못하는 상황이 생긴다.

### 다형성 (Polymorphism)

같은 타입의 참조변수로 여러 형태의 객체를 다룰 수 있는 성질이다.

**컴파일 타임 다형성 (오버로딩, Overloading)**

```java
public int add(int a, int b)          { return a + b; }
public double add(double a, double b) { return a + b; }
```

메서드 시그니처(이름 + 파라미터 타입/개수)로 컴파일 시점에 어떤 메서드를 호출할지 결정된다. 반환 타입만 다른 오버로딩은 불가하다.

```java
class Animal {}
class Dog extends Animal {}

void print(Animal a) { System.out.println("Animal"); }
void print(Dog d) { System.out.println("Dog"); }

Animal a = new Dog();
print(a);  // "Animal" — 참조 변수의 선언 타입 기준으로 컴파일 타임에 결정(정적 바인딩)
```

`a`의 실제 객체는 `Dog`이지만, 오버로딩은 **참조 변수의 선언 타입**을 기준으로 컴파일 시점에 정해지는 정적 바인딩이라 `print(Animal)`이 호출된다. 이게 아래 오버라이딩(동적 바인딩)과 정반대되는 지점이다.

**런타임 다형성 (오버라이딩, Overriding)**

```java
Animal animal = new Dog();  // 부모 타입 참조 → 자식 객체
animal.sound();             // 런타임에 Dog.sound() 호출 — 동적 디스패치
```

JVM은 참조 변수 타입이 아니라 실제 객체 타입을 기준으로 메서드를 선택한다(가상 메서드 테이블, vtable). 이것이 **동적 디스패치(Dynamic Dispatch)**다.

**다형성이 적용되지 않는 경우 — 필드 섀도잉**

메서드와 달리 **필드**는 오버라이딩되지 않고 **섀도잉(shadowing)** 된다.

```java
class Animal { String name = "Animal"; }
class Dog extends Animal { String name = "Dog"; }

Animal a = new Dog();
System.out.println(a.name);  // "Animal" — 참조 타입 기준
```

`Dog`는 `Animal.name`과 `Dog.name`을 각각 별도의 메모리 슬롯으로 둘 다 가지고 있고, 어느 필드에 접근할지는 순전히 참조 변수의 선언 타입에 따라 정해진다. vtable에는 메서드 슬롯만 있고 필드 슬롯은 없으므로, 필드는 애초에 동적 디스패치(다형성)의 대상이 될 수 없다.

### 추상화 (Abstraction)

복잡한 구현을 숨기고 필요한 인터페이스(계약)만 노출하는 것이다. Java에서는 `abstract class`와 `interface`로 구현한다.

```java
public abstract class Shape {
    public abstract double area();  // 구현은 자식에게 위임

    public void printArea() {       // 공통 구현은 여기서 제공
        System.out.println("area = " + area());
    }
}

public class Circle extends Shape {
    private final double radius;
    public Circle(double radius) { this.radius = radius; }

    @Override
    public double area() { return Math.PI * radius * radius; }
}
```

`printArea()`를 호출하는 코드는 `area()`가 원의 넓이 공식인지 사각형의 넓이 공식인지 전혀 알 필요가 없다 — "넓이를 구할 수 있다"는 계약만 알면 된다. **왜 필요한가?** 호출하는 쪽(클라이언트 코드)이 구현 세부사항에 의존하지 않게 되어, 구현이 바뀌거나 늘어나도 호출부는 그대로 유지된다. 다형성이 "여러 구현을 하나의 타입으로 다룰 수 있게" 해주는 메커니즘이라면, 추상화는 "그 하나의 타입이 무엇을 약속하는가"를 정의하는 역할이다.

## 인터페이스 vs 추상 클래스

| 비교 항목 | 인터페이스 | 추상 클래스 |
|---|---|---|
| 목적 | 능력(can-do) 명세 | 정체성(is-a) + 공통 구현 |
| 다중 구현 | O | X (단일 상속) |
| 필드 | `public static final`만 | 모든 접근 제어자 |
| 생성자 | X | O |
| `default` 메서드 | O (Java 8+) | O |
| `static` 메서드 | O (Java 8+) | O |

**언제 무엇을 선택하는가?**

```
"Dog는 Animal이다(is-a)" → 추상 클래스 Animal
"Dog는 수영할 수 있다(can-do)" → 인터페이스 Swimmable
```

인터페이스는 **다중 구현**이 가능하므로, 기능 계약을 타입으로 분리할 때 쓴다. 추상 클래스는 공통 상태(필드)나 부분 구현을 공유해야 할 때 쓴다.

**왜 클래스는 단일 상속만 가능한가?** 두 부모가 같은 이름의 **필드**를 가질 때 어떤 값을 물려받을지 모호해지는 "다이아몬드 문제"가 발생하기 때문이다. 인터페이스는 (Java 8 이전) 필드가 없는 순수 계약이었기 때문에 다중 구현이 허용됐다.

**Java 8 이후 default 메서드**

```java
interface Printable {
    void print();

    default void printWithBorder() {  // 구현체에 강제하지 않는 선택적 기능
        System.out.println("---");
        print();
        System.out.println("---");
    }
}
```

기존 인터페이스에 메서드를 추가해도 구현체가 깨지지 않도록 하기 위해 도입됐다. 단, 두 인터페이스에 같은 시그니처의 `default` 메서드가 있으면 컴파일러가 어느 쪽을 써야 할지 알 수 없으므로, 구현 클래스에서 반드시 오버라이딩해야 한다(다이아몬드 문제).

## 조합(Composition) vs 상속(Inheritance)

GoF는 "상속보다 조합을 선호하라"고 말한다.

**상속의 문제점**

```java
// 상위 클래스 내부 구현에 강하게 결합된다
public class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);  // 내부적으로 add()를 호출하므로 addCount가 두 번 증가
    }
}
```

`addAll()`이 `addCount += c.size()`를 실행한 뒤 `super.addAll(c)`(`HashSet.addAll()`)를 호출하는데, `HashSet.addAll()` 내부는 원소마다 `add()`를 호출한다. 이때 호출되는 `add()`는 실제 객체 타입 기준 동적 디스패치로 인해 `InstrumentedHashSet.add()`가 호출되어 `addCount`가 원소 개수만큼 다시 증가한다. `addAll()`에서 한 번, 내부 `add()` 호출마다 또 한 번씩 이중으로 카운트되는 것이다 — 상위 클래스 내부 구현(`addAll()`이 `add()`를 호출한다는 세부사항)에 강하게 결합됐기 때문에 생긴 버그다.

**조합으로 해결**

```java
public class InstrumentedSet<E> implements Set<E> {
    private final Set<E> set;     // 조합 — 내부에 포함
    private int addCount = 0;

    public InstrumentedSet(Set<E> set) { this.set = set; }

    @Override public boolean add(E e) {
        addCount++;
        return set.add(e);
    }

    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return set.addAll(c);  // 위임, 내부 구현에 무관
    }
    // ... 나머지 Set 메서드들을 set에 위임
}
```

내부에 `Set` 인스턴스를 필드로 두고 위임(delegate)하므로, 위임 대상의 구현이 내부적으로 `add()`를 호출하든 말든 자신의 `addCount` 로직에 영향을 주지 않는다.

## equals()와 hashCode() 계약

Collection에서 객체 동등성을 올바르게 동작시키려면 반드시 함께 오버라이딩해야 한다.

**equals() 계약 (Object 명세)**
- 반사성(reflexive): `x.equals(x)` = true
- 대칭성(symmetric): `x.equals(y)` = true이면 `y.equals(x)` = true
- 추이성(transitive): `x.equals(y)`, `y.equals(z)` → `x.equals(z)` = true
- 일관성(consistent): 반복 호출 시 동일 결과
- null 비교: `x.equals(null)` = false

**hashCode() 계약**
- `equals()`가 true인 두 객체는 반드시 같은 hashCode를 반환해야 한다
- `equals()`가 false인 두 객체가 같은 hashCode를 반환할 수 있다 (충돌)
- `hashCode()`가 다르면 반드시 `equals()`는 false다

**왜 함께 오버라이딩해야 하는가?**

```java
public class Point {
    int x, y;

    @Override public boolean equals(Object o) {
        if (!(o instanceof Point)) return false;
        Point p = (Point) o;
        return x == p.x && y == p.y;
    }
    // hashCode 오버라이딩 안 함!
}

Set<Point> set = new HashSet<>();
set.add(new Point(1, 2));
set.contains(new Point(1, 2));  // false! — hashCode가 달라 다른 버킷에 배치
```

`HashMap`/`HashSet`은 먼저 `hashCode()`로 버킷을 찾고, 그 안에서 `equals()`로 비교한다. `hashCode()`를 오버라이딩하지 않으면 Object의 기본 구현(메모리 주소 기반)이 사용되어 논리적으로 같은 객체가 다른 버킷에 들어간다.

**상속 관계에서 equals()의 대칭성이 깨지는 경우**

`Point`를 상속해 색상 필드를 추가한 `ColorPoint`가 있고, `ColorPoint.equals()`를 "색상까지 같아야 같다"로 오버라이딩했다고 하자.

```java
Point p1 = new Point(2, 3);
ColorPoint c1 = new ColorPoint(2, 3, RED);

p1.equals(c1);  // Point.equals()가 실행 — instanceof Point로 체크, 좌표만 보고 true
c1.equals(p1);  // ColorPoint.equals()가 실행 — 색상까지 요구, p1엔 색상이 없어 false
```

`x.equals(y)`와 `y.equals(x)`가 서로 달라 **대칭성이 깨진다.** 해결책으로 `instanceof` 대신 `getClass()`로 정확히 같은 클래스인지 비교하는 방법이 있지만, 이번엔 다른 문제가 생긴다. 좌표가 같아도 클래스가 다르다는 이유만으로 `equals()`가 항상 `false`가 되어, `Point`를 매개변수로 받는 코드가 서브클래스를 대신 넣었을 때 다르게 동작한다 — **리스코프 치환 원칙(LSP) 위반**이다.

근본 해결책은 상속 자체를 포기하는 것이다. `ColorPoint`가 `Point`를 상속하는 대신 `Point`를 필드로 가지는 **조합** 구조로 바꾸면, 상속 계층과 무관하게 `equals()`를 독립적으로 올바르게 정의할 수 있다 — "상속보다 조합" 원칙이 `equals()` 설계에도 그대로 적용되는 셈이다. (단, 상속 관계가 아예 없는 두 클래스라면 `instanceof`와 `getClass()`의 결과가 항상 같으므로 이 딜레마 자체가 발생하지 않는다.)

## 불변(Immutable) 객체 설계

**얕은 복사 vs 깊은 복사**

`Object.clone()`은 기본적으로 **얕은 복사(shallow copy)** 를 수행한다 — 필드 값(참조값) 자체만 복사한다.

```java
class Address { String city; }
class Person implements Cloneable {
    String name;
    Address address;

    @Override
    protected Person clone() throws CloneNotSupportedException {
        return (Person) super.clone();  // 얕은 복사
    }
}

Person p1 = new Person();
Person p2 = p1.clone();
p2.address.city = "Busan";
System.out.println(p1.address.city);  // "Busan" — 같은 Address 객체를 공유하기 때문
```

`Address`처럼 참조 타입 필드는 원본과 복사본이 같은 객체를 가리키게 되어, 한쪽에서 내부 상태를 바꾸면 다른 쪽에도 영향을 준다. **깊은 복사(deep copy)** 는 `Address` 객체 자체도 새로 만들어 복사본에 연결해야 하며, 그래야 두 객체가 서로 독립적인 상태를 가질 수 있다.

```java
@Override
protected Person clone() throws CloneNotSupportedException {
    Person copy = (Person) super.clone();
    copy.address = new Address();
    copy.address.city = this.address.city;  // Address도 새로 생성 — 깊은 복사
    return copy;
}
```

**불변 클래스를 만들 때 지켜야 할 조건**

- 모든 필드를 `private final`로 선언하고 생성자에서만 초기화한다(setter 없음)
- 클래스 자체를 확장 불가능하게 만든다(`final class`, 또는 생성자를 `private`으로 감추고 정적 팩터리 제공). 그렇지 않으면 자식 클래스가 새 가변 상태를 추가하거나 `equals()`/`hashCode()`를 오버라이딩해 불변성이 깨질 수 있다
- 가변 객체를 참조하는 필드가 있다면(예: `Date`), **생성자와 getter 양쪽 모두에서** 방어적 복사(defensive copy)를 해야 한다

```java
public final class Person {
    private final String name;
    private final Date birthDate;

    public Person(String name, Date birthDate) {
        this.name = name;
        this.birthDate = new Date(birthDate.getTime());  // 들어오는 시점에 복사
    }

    public Date getBirthDate() {
        return new Date(birthDate.getTime());  // 나가는 시점에 복사
    }
}
```

생성자에서 `this.birthDate = birthDate;`처럼 받은 참조를 그대로 저장하면, 호출자가 생성자에 넘겼던 원본 객체에 대한 참조를 여전히 가지고 있다. 객체 생성 후 호출자가 그 원본을 `birth.setTime(0)`처럼 직접 바꾸면, 우리 클래스의 어떤 메서드도 거치지 않은 채 내부 상태가 바뀐다. getter에서만 방어적 복사를 해도 생성자 쪽이 뚫려 있으면 반쪽짜리 불변성이므로, 양쪽 다 복사해야 한다.

**왜 불변 객체는 스레드 안전한가?**

`synchronized`나 락은 "여러 스레드가 동시에 읽는 도중 하나가 쓰면 그 상태가 꼬이는" 레이스 컨디션을 막기 위한 장치다. 불변 객체는 생성 이후 상태를 바꾸는 연산 자체가 존재하지 않으므로 "쓰기"라는 이벤트가 애초에 발생하지 않는다. 어떤 스레드가 그 객체를 참조하든 항상 생성 시점에 완성된, 변하지 않는 상태만 보게 되므로 레이스 컨디션이 발생할 조건 자체가 성립하지 않는다. (`final` 필드는 자바 메모리 모델(JMM)상 생성자가 끝난 시점에 다른 스레드에서도 그 값이 올바르게 보이도록 보장하는 규칙이 있어, 불변 객체를 스레드 간에 안전하게 공유하는 데 한몫한다.)

## SOLID 원칙

OOP 설계 원칙 다섯 가지. 다형성·조합·캡슐화 논의와 자연스럽게 이어진다.

| 원칙 | 이름 | 한 줄 설명 |
|---|---|---|
| SRP | 단일 책임 원칙 | 클래스는 하나의 책임(변경 이유)만 가져야 한다 |
| OCP | 개방-폐쇄 원칙 | 확장에는 열려있고, 기존 코드 수정에는 닫혀있어야 한다 |
| LSP | 리스코프 치환 원칙 | 자식 클래스는 부모 타입 자리에 대체 투입되어도 프로그램의 정확성을 깨서는 안 된다 |
| ISP | 인터페이스 분리 원칙 | 클라이언트는 자신이 사용하지 않는 메서드에 의존하도록 강요받아서는 안 된다 |
| DIP | 의존관계 역전 원칙 | 상위 모듈과 하위 모듈 모두 구체 클래스가 아닌 추상화(인터페이스)에 의존해야 한다 |

**SRP 예시 — 책임이 뒤섞인 클래스**

```java
// 위반: 주문 검증 + 결제 + 이메일 발송이 한 클래스에 뒤섞임
class OrderProcessor {
    void validate(Order order) { ... }
    void charge(Order order) { ... }
    void sendConfirmationEmail(Order order) { ... }
}

// 준수: 책임 단위로 분리
class OrderValidator { void validate(Order order) { ... } }
class PaymentService { void charge(Order order) { ... } }
class EmailNotifier { void sendConfirmationEmail(Order order) { ... } }
```

이메일 발송 로직이 바뀌었을 뿐인데 결제 로직까지 들어있는 `OrderProcessor` 전체를 다시 테스트해야 한다면, 그건 책임이 한곳에 너무 많이 뭉쳐 있다는 신호다.

**OCP 예시 — 결제 수단 분기**

```java
// 위반: 새 결제 수단이 추가될 때마다 기존 코드를 수정해야 한다
if (type == CARD) { ... }
else if (type == TRANSFER) { ... }
else if (type == VIRTUAL_ACCOUNT) { ... }  // 추가할 때마다 여기 수정

// 준수: 다형성으로 확장, 기존 코드는 그대로
interface PaymentMethod { void pay(long amount); }
class CardPayment implements PaymentMethod { ... }
class VirtualAccountPayment implements PaymentMethod { ... }  // 새 클래스만 추가
```

**LSP 위반 사례 — 정사각형은 직사각형을 상속해야 하는가**

`Rectangle`은 `setWidth()`와 `setHeight()`가 서로 독립적으로 동작한다는 암묵적 계약을 가진다. `Square`는 가로·세로가 항상 같아야 하므로 `setWidth()` 호출 시 `height`도 함께 바뀐다. `Rectangle` 타입을 기대하고 "`setWidth(5); setHeight(4);` 후 넓이는 20"이라고 가정한 코드는 `Square` 객체가 들어오는 순간 깨진다. 상속 관계(is-a)는 성립해도 행동 계약이 달라 LSP를 위반하는 대표적인 예다.

**ISP 예시**

```java
// 위반: 로봇은 먹지 않는데 eat()를 강제로 구현해야 한다
interface Worker { void work(); void eat(); }
class RobotWorker implements Worker {
    public void work() { ... }
    public void eat() { throw new UnsupportedOperationException(); }  // 억지 구현
}

// 준수: 인터페이스를 역할 단위로 분리
interface Workable { void work(); }
interface Eatable { void eat(); }
class RobotWorker implements Workable { public void work() { ... } }
```

**DIP와 스프링 DI**

상위 모듈(도메인 로직)이 하위 모듈(구체적인 DB 접근, 외부 API 구현체)에 직접 의존하면, 하위 모듈이 바뀔 때마다 상위 모듈도 함께 흔들린다. 인터페이스라는 추상화를 사이에 두고 양쪽 다 그 추상화에 의존하도록 하면 구현체 교체가 상위 로직에 영향을 주지 않는다. 스프링의 `@Autowired`/DI 컨테이너는 이 원칙을 프레임워크 차원에서 자동화한 것으로, 빈은 인터페이스에 의존하고 실제 구현체는 컨테이너가 런타임에 주입한다.

**응집도(Cohesion)와 결합도(Coupling) — SOLID가 실제로 낮추려는 것**

응집도는 한 클래스 안에 서로 관련된 기능들이 얼마나 뭉쳐 있는지를, 결합도는 한 클래스가 다른 클래스에 얼마나 세세하게 의존하는지를 나타낸다. 응집도가 낮으면(관련 없는 책임들이 한 클래스에 뒤섞여 있으면) 기능 하나만 고치려 해도 그 클래스 전체에 영향이 갈 위험이 있고, 결합도가 높으면 그 클래스에 의존하는 다른 클래스들까지 연쇄적으로(ripple effect) 영향을 받아 수정 범위가 눈덩이처럼 불어난다. SRP는 응집도를 높이는 데, DIP는 결합도를 낮추는 데 직접 기여하는 원칙이다 — 결국 SOLID 다섯 가지는 "높은 응집도, 낮은 결합도"라는 하나의 목표를 서로 다른 각도에서 달성하는 방법들이다.

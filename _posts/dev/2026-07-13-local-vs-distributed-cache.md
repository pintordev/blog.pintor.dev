## Summary

- **로컬 캐시**: 애플리케이션 프로세스의 메모리 안에 존재 — 접근 속도가 가장 빠르지만 인스턴스마다 독립적이라 데이터 불일치가 발생할 수 있다.
- **분산 캐시**: 별도 인프라(Redis, Memcached 등)에 존재 — 모든 인스턴스가 하나의 캐시를 공유해 일관성을 유지하지만 네트워크 왕복 비용이 붙는다.
- 선택 기준은 결국 **일관성 요구 수준**과 **인스턴스 확장 규모**의 트레이드오프다.

---

## Background

애플리케이션이 단일 서버로 운영될 때는 캐시를 어디에 둘지 고민할 필요가 크지 않다. 프로세스 메모리에 두면 그만이다. 하지만 트래픽이 늘어 서버를 여러 대로 수평 확장(scale-out)하면, 각 인스턴스가 각자의 메모리에 캐시를 들고 있는 것과, 모든 인스턴스가 캐시를 공유하는 것 사이에 선택이 필요해진다. 이 선택이 바로 로컬 캐시와 분산 캐시의 갈림길이다.

---

## 로컬 캐시 (Local Cache / In-Process Cache)

애플리케이션과 동일한 프로세스의 힙 메모리(또는 오프힙)에 캐시 데이터를 저장하는 방식이다. 대표 구현체로 Caffeine, Guava Cache, Ehcache가 있다.

```java
Cache<Long, Product> cache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(10))
    .build();

Product product = cache.get(productId, id -> productRepository.findById(id));
```

**장점**
- 네트워크 호출이 없어 접근 속도가 마이크로초 단위로 가장 빠르다.
- 별도 인프라가 필요 없어 구성이 단순하고 인프라 비용이 없다.
- 캐시 서버 장애가 애플리케이션 전체에 영향을 주지 않는다(장애 격리).

**단점**
- 인스턴스마다 캐시가 독립적이라, 서버 A에서 갱신한 데이터가 서버 B의 캐시에는 반영되지 않는 **캐시 불일치(incoherence)** 문제가 생긴다.
- 인스턴스 수만큼 메모리를 중복 사용한다(예: 캐시 10MB × 인스턴스 20대 = 200MB 중복).
- 인스턴스가 재시작되면 해당 인스턴스의 캐시는 완전히 초기화된다(cold start).

---

## 분산 캐시 (Distributed Cache)

애플리케이션과 분리된 별도의 캐시 서버(또는 클러스터)에 데이터를 저장하고, 모든 애플리케이션 인스턴스가 네트워크를 통해 이 캐시를 공유하는 방식이다. Redis, Memcached가 대표적이다.

```java
@Cacheable(value = "products", key = "#id", cacheManager = "redisCacheManager")
public Product findById(Long id) {
    return productRepository.findById(id).orElseThrow();
}
```

**장점**
- 모든 인스턴스가 동일한 캐시를 바라보므로 일관성이 보장된다.
- 인스턴스를 몇 대로 늘려도 캐시 데이터는 중복 저장되지 않는다.
- 애플리케이션이 재시작되어도 캐시 데이터는 유지된다(캐시 서버가 살아있는 한).
- Redis의 경우 TTL, Pub/Sub, 원자적 연산(`INCR` 등) 같은 부가 기능도 함께 활용 가능.

**단점**
- 네트워크 왕복이 필요해 로컬 캐시보다 느리다(보통 수백 마이크로초~수 밀리초).
- 캐시 서버가 별도의 장애 지점(SPOF)이 된다 — Redis 장애 시 모든 인스턴스가 영향을 받는다.
- 별도 인프라 운영/모니터링 비용이 발생한다.

## 비교 요약

| 항목 | 로컬 캐시 | 분산 캐시 |
|---|---|---|
| 저장 위치 | 애플리케이션 프로세스 메모리 | 별도 캐시 서버/클러스터 |
| 접근 속도 | 매우 빠름 (마이크로초) | 상대적으로 느림 (네트워크 왕복 포함) |
| 일관성 | 인스턴스 간 불일치 가능 | 모든 인스턴스가 동일한 데이터 공유 |
| 확장성 | 인스턴스마다 메모리 중복 | 인스턴스 수와 무관하게 단일 저장소 |
| 장애 영향 범위 | 해당 인스턴스에 국한 | 캐시 서버 장애 시 전체 영향 |
| 인프라 비용 | 없음 (프로세스 메모리 활용) | 별도 서버/클러스터 필요 |
| 재시작 시 데이터 | 소실 (cold start) | 유지 (캐시 서버가 살아있는 한) |
| 대표 구현체 | Caffeine, Guava Cache, Ehcache | Redis, Memcached |

## 하이브리드 전략: 2-Level Cache (Near Cache)

두 방식을 함께 쓰는 구조도 실무에서 흔하다. 로컬 캐시를 1차(L1), 분산 캐시를 2차(L2)로 두는 방식이다.

```
요청 → L1(로컬 캐시) 조회
         │ 히트 → 즉시 반환 (가장 빠름)
         │ 미스
         ↓
       L2(분산 캐시, Redis) 조회
         │ 히트 → L1에 채우고 반환
         │ 미스
         ↓
       DB 조회 → L1, L2 모두 채우고 반환
```

이 구조는 대부분의 요청을 로컬 캐시에서 초고속으로 처리하면서도, L2를 통해 인스턴스 간 데이터 정합성을 어느 정도 확보할 수 있다. 다만 L1의 데이터가 L2보다 먼저 갱신되거나 늦게 무효화되는 시점에는 여전히 일시적인 불일치가 생길 수 있어, Redis의 Pub/Sub으로 캐시 무효화 이벤트를 각 인스턴스에 전파하는 방식을 함께 쓰기도 한다.

## 실무 선택 기준

| 상황 | 권장 |
|---|---|
| 변경이 거의 없는 참조 데이터(코드 테이블, 설정값) | 로컬 캐시 |
| 여러 인스턴스 간 즉각적인 데이터 일관성이 중요한 경우(재고, 좌석) | 분산 캐시 |
| 조회 트래픽이 극도로 많고 지연에 민감한 경우 | 로컬 캐시 또는 2-Level |
| 세션 데이터처럼 여러 서버가 공유해야 하는 상태 | 분산 캐시 |
| 단일 인스턴스 또는 소규모 운영 환경 | 로컬 캐시로 충분 |
| 대규모 수평 확장 환경, 데이터 정합성이 중요 | 분산 캐시(또는 하이브리드) |

캐시를 도입하는 목적이 "속도"인지 "부하 분산과 공유 상태 유지"인지를 먼저 구분하는 것이 선택의 출발점이다. 단순히 DB 부하를 줄이는 것이 목적이고 약간의 지연된 일관성(eventual consistency)을 감수할 수 있다면 로컬 캐시만으로 충분한 경우가 많다.

---

## Key Point

> **로컬 캐시는 속도를, 분산 캐시는 일관성과 공유를 산다. 인스턴스가 하나뿐이거나 데이터가 거의 바뀌지 않는다면 로컬 캐시로 충분하지만, 여러 인스턴스가 같은 상태를 실시간으로 공유해야 한다면 분산 캐시 없이는 정합성을 보장할 수 없다. 두 요구가 동시에 강하다면 로컬을 L1, 분산을 L2로 두는 하이브리드 구조를 고려해야 한다.**

## Summary

- **TCP**: 연결 지향(connection-oriented), 신뢰성 있는 전달을 보장하는 프로토콜. 3-way handshake로 연결을 맺고, 순서 보장과 재전송으로 데이터 무결성을 지킨다.
- **UDP**: 비연결형(connectionless), 신뢰성을 보장하지 않는 대신 오버헤드가 적고 빠른 프로토콜.
- 선택 기준은 "정확성이 중요한가, 실시간성이 중요한가"로 요약된다.

---

## Background

전송 계층(Transport Layer)의 역할은 애플리케이션 간에 데이터를 종단 간(end-to-end)으로 전달하는 것이다. 그런데 애플리케이션마다 요구사항이 다르다. 파일 전송이나 웹 페이지 로딩처럼 데이터가 하나라도 유실되거나 순서가 뒤바뀌면 안 되는 경우가 있는 반면, 실시간 음성/영상 통화처럼 약간의 데이터 유실보다 지연(latency)이 더 치명적인 경우도 있다.

이 상반된 요구를 하나의 프로토콜로 만족시키기 어려웠기 때문에, IETF는 신뢰성을 극대화한 **TCP(Transmission Control Protocol)**와 최소한의 오버헤드로 속도를 극대화한 **UDP(User Datagram Protocol)**를 별도로 표준화했다. 두 프로토콜 모두 IP 위에서 동작하지만, 제공하는 보장의 수준이 근본적으로 다르다.

## TCP (Transmission Control Protocol)

### 연결 수립: 3-way Handshake

TCP는 데이터를 주고받기 전에 반드시 연결을 먼저 수립한다.

```
Client                     Server
  | ----- SYN --------------> |
  | <---- SYN + ACK --------- |
  | ----- ACK --------------> |
```

1. 클라이언트가 SYN(연결 요청)을 보낸다.
2. 서버가 SYN을 수신했음을 알리며 자신도 SYN을 보내는 SYN+ACK로 응답한다.
3. 클라이언트가 다시 ACK를 보내 연결이 확정된다.

이 과정을 통해 양쪽 모두 상대방의 송수신 가능 여부를 확인하고, 초기 시퀀스 번호(sequence number)를 교환해 이후 데이터의 순서를 추적할 준비를 마친다.

### 신뢰성 보장 메커니즘

| 메커니즘 | 설명 |
|---|---|
| 순서 제어(Sequencing) | 각 세그먼트에 시퀀스 번호를 부여해 수신 측에서 원래 순서로 재조립 |
| 재전송(Retransmission) | ACK가 일정 시간 내 도착하지 않으면 세그먼트를 다시 전송 |
| 흐름 제어(Flow Control) | 수신 측 버퍼 상태(window size)에 맞춰 송신 속도 조절 |
| 혼잡 제어(Congestion Control) | 네트워크 혼잡 상황을 감지해 전송량을 동적으로 조절 |
| 오류 검출 | 체크섬으로 손상된 세그먼트 탐지 후 재전송 요청 |

이러한 보장 덕분에 애플리케이션은 데이터가 보낸 순서 그대로, 손실 없이 도착한다고 신뢰할 수 있다. 대신 handshake, ACK 대기, 재전송 등의 과정에서 지연과 오버헤드가 발생한다.

## UDP (User Datagram Protocol)

UDP는 연결 수립 과정 없이 데이터그램(datagram)을 그대로 보낸다. 헤더 구조도 TCP보다 단순하다.

```
UDP 헤더: 출발지 포트 | 목적지 포트 | 길이 | 체크섬   (8바이트 고정)
TCP 헤더: 출발지 포트 | 목적지 포트 | 시퀀스 번호 | ACK 번호 |
          플래그 | 윈도우 크기 | 체크섬 | 긴급 포인터 | 옵션  (최소 20바이트)
```

- 연결 수립 과정이 없어 첫 패킷부터 바로 데이터를 실어 보낼 수 있다(낮은 지연).
- 도착 순서를 보장하지 않고, 유실되어도 재전송하지 않는다.
- 흐름 제어·혼잡 제어가 없어 네트워크 상황과 무관하게 일정한 속도로 전송한다.
- 신뢰성 보장이 필요하다면 애플리케이션 계층에서 직접 구현해야 한다(예: 실시간 스트리밍의 자체 오류 은닉 로직).

## TCP vs UDP 비교

| 구분 | TCP | UDP |
|---|---|---|
| 연결 방식 | 연결 지향 (3-way handshake) | 비연결형 |
| 신뢰성 | 보장 (순서, 재전송, 오류 검출) | 보장하지 않음 |
| 전송 순서 | 보장 | 보장하지 않음 |
| 속도 | 상대적으로 느림 (오버헤드 존재) | 상대적으로 빠름 |
| 헤더 크기 | 최소 20바이트 | 8바이트 |
| 흐름/혼잡 제어 | 있음 | 없음 |
| 단위 | 세그먼트(Segment) | 데이터그램(Datagram) |
| 대표 사용처 | HTTP, FTP, 이메일(SMTP), DB 연결 | DNS, 스트리밍, 온라인 게임, VoIP |

## 언제 무엇을 쓸까

**TCP가 적합한 경우**

- 파일 다운로드/업로드: 바이트 하나라도 누락되면 파일이 손상된다.
- 웹 통신(HTTP/HTTPS): 요청·응답이 정확히 전달되어야 한다.
- 데이터베이스 연결: 쿼리 결과의 순서와 무결성이 중요하다.

**UDP가 적합한 경우**

- 실시간 음성/영상 통화(VoIP, 화상회의): 패킷 하나가 늦게 도착하느니 차라리 버리고 다음 프레임으로 넘어가는 게 낫다.
- 온라인 게임의 위치 동기화: 오래된 위치 정보를 재전송받는 것보다 최신 정보를 빨리 받는 게 중요하다.
- DNS 조회: 요청/응답이 짧고, 실패 시 애플리케이션이 간단히 재요청하면 되므로 handshake 오버헤드가 낭비다.
- 스트리밍(라이브 방송): 약간의 프레임 손실은 허용되지만 지연은 체감 품질에 직결된다.

---

## Key Point

> **TCP는 "정확하게, 순서대로, 반드시" 전달해야 하는 데이터에, UDP는 "빠르게, 지금 당장" 전달해야 하는 데이터에 적합하다. TCP의 신뢰성은 3-way handshake, 시퀀스 번호, 재전송, 흐름/혼잡 제어라는 오버헤드의 대가로 얻어지며, UDP는 이 모든 것을 생략해 최소 지연을 확보하는 대신 신뢰성을 애플리케이션 몫으로 넘긴다. 선택 기준은 결국 "데이터 무결성"과 "실시간성" 중 어느 쪽이 더 치명적인가에 달려 있다.**

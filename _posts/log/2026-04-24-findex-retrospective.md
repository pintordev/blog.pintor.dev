## 프로젝트 개요

한국 주가지수 분석 백엔드 서비스 **Findex**를 6인 팀으로 개발했다. 금융위원회 공공데이터 Open API에서 지수 데이터를 수집하고, 이동평균·등락률 같은 금융 지표를 계산해 제공하는 Spring Boot 백엔드다. Railway.io에 실서비스로 배포까지 했다.

나는 팀장을 맡았고, 도메인으로는 **M1(지수 정보 CRUD, 목록 조회)** 을 담당하면서 대시보드 성능 개선, DB 인덱스 적용, 공통 인프라 작업을 추가로 진행했다.

---

## 내가 한 것들

### M1 — 지수 정보 CRUD + 커서 기반 목록 조회

가장 처음에 잡은 도메인이라 설계 결정이 팀 전체에 영향을 미쳤다. M1 엔티티를 결정해야 다른 팀원들의 작업이 진행될 수 있는 구조였다.

커서 페이지네이션 방식과 QueryDSL Custom Repository 패턴은 이를 사용하는 팀원들과 개발 작업 착수 전에 회의를 통해 결정했다.

커서 페이지네이션은 `cursor`(정렬 필드 값) + `idAfter`(UUID tiebreaker) 복합 구조로 구현했다. 같은 정렬 값이 여러 건일 때 ID로 순서를 확정하는 방식인데, 정렬 필드 타입이 `String`과 `Integer`로 달라서 `ComparableExpression`과 `NumberExpression`을 오버로딩으로 분리해야 했다. 처음엔 단순해 보였는데 타입 분기, DESC 방향 tiebreaker 처리, `idAfter == null` NPE 방지까지 생각보다 신경 쓸 게 많았다.

### H2 vs PostgreSQL ORDER BY 미보장

가장 당황스러웠던 버그다. 로컬에서는 요약 목록이 항상 같은 순서로 나왔는데, 배포 환경(PostgreSQL)에서는 호출마다 순서가 달라졌다. H2는 삽입 순서를 기본으로 반환하지만 PostgreSQL은 `ORDER BY` 없이 순서를 보장하지 않는다는 걸 이때 처음 몸으로 배웠다. `ORDER BY` 한 줄 추가로 해결됐지만, "로컬에서 됐는데"라는 말이 얼마나 위험한지를 새삼 느꼈다.

### Dashboard N+1 쿼리 제거

팀에서 가장 임팩트 있었던 작업이다. 즐겨찾기 성과 조회 API에서 지수 200개 기준 쿼리가 **201개** 발생하고 있었다. 루프 안에서 지수별로 `IndexData`를 개별 조회하는 전형적인 N+1 패턴이었다.

`In-Clause` + `fetchJoin()` 조합으로 단일 배치 쿼리로 전환하고, DB에서 전체를 한 번에 가져온 뒤 Java Stream `groupingBy`로 메모리 내 그룹화·연산하는 방식으로 바꿨다.

| 구분 | Before | After | 개선율 |
| --- | --- | --- | --- |
| 쿼리 수 | 201개 | 1개 | 99.5% 감소 |
| DAILY 응답 | 84ms | 8ms | 90.5% 감소 |

프로젝트를 하면 숫자로 나오는 성능을 중요시 여기는데 그동안 진행했던 프로젝트에서는 체크하지 못했던 부분을 이번에 처음 진행해봤는데 실제 결과로 이어져서 좋았다.

### DB 인덱스 적용

430만 건 `index_data`, 12만 건 `sync_job`이 쌓인 상황에서 인덱스를 점검했다. `EXPLAIN ANALYZE`를 처음 제대로 써본 작업이었다. `sync_job` 마지막 성공 날짜 조회가 Sequential Scan을 타고 있던 걸 부분 인덱스(Partial Index)로 교체하니 **20.59ms → 0.10ms**, 99.5% 개선이 나왔다. Index Only Scan으로 전환된 수행 계획을 보는 순간이 이 프로젝트에서 가장 인상적인 장면 중 하나였다.

### 이동평균 슬라이딩 윈도우

MA5/MA20 계산이 매 포인트마다 윈도우 전체를 재합산하는 O(n×k) 이중 루프였다. 슬라이딩 윈도우로 바꿔 O(n)으로 줄였다. 알고리즘 공부에서 봤던 내용을 실제 코드에 적용하니 느낌이 달랐다.

다만 현재 서비스에 쌓인 실 데이터가 충분하지 않아 측정 가능한 응답시간 차이는 나오지 않았다. 코드 구조 자체는 맞는 방향이라고 생각하고, 데이터가 쌓일수록 효과가 나타날 것이다. "최적화가 의미 없었다"는 뜻이 아니라, 지금 당장 수치로 검증하기 어려웠다는 뜻이다.

### count 쿼리 최적화

모든 페이지 요청마다 `totalElements` count 쿼리를 실행하던 구조를 `cursor == null`인 첫 페이지에서만 실행하도록 변경했다. 이후 페이지는 count를 생략하고 `totalElements: null`을 반환하며 클라이언트가 초기 값을 재사용한다. 5000페이지 기준 오프셋 대비 37.8% 응답 개선. "항상 count를 반환해야 한다"는 고정관념을 한번 의심하고 나니 보였던 개선이었다.

## 팀장으로서의 경험

**No communication, No responsibility**

팀장은 이번이 처음이 아니었다. 그런데 이 팀만큼 팀원들이 잘 따라와준 경험은 처음이었다.

처음 정해둔 개발 컨벤션에 잘 맞춰줬고, ADR을 써서 결정 근거를 남기는 것에도 잘 따라줬다. 리뷰 코멘트에도 건설적인 토론이 진행되었고, 2 approvals 룰도 불만 없이 지켜줬다. 덕분에 팀 관리가 아닌 기술 결정과 공통 작업에 전념할 수 있었다.

이전에 팀장을 해본 경험과 비교하면, 결국 팀 분위기는 시스템(컨벤션, 문서, 리뷰 프로세스)이 만드는 것과 사람이 만드는 것이 반반이라는 생각이 든다. 시스템을 잘 깔아줘도 따라오지 않으면 소용없고, 사람이 좋아도 시스템이 없으면 각자 다른 방향으로 달린다. 이번엔 둘 다 맞아떨어진 케이스였다.

## 아쉬웠던 것들

**테스트 커버리지.** 비즈니스 로직보다 인프라 연결에 시간을 많이 썼다. 초반부터 단위 테스트를 촘촘하게 짰다면 중간 리그레션을 더 빠르게 잡을 수 있었을 것 같다.

**커서 페이지네이션 깊은 페이지 성능.** 5000페이지에서도 커서가 선형 증가하는 문제가 남아있다. OR 조건이 복합 인덱스 range scan을 타지 못하는 구조적 한계로 추정되는데, 시간 안에 완전히 해결하지 못했다.

## 배운 것들 정리

`EXPLAIN ANALYZE`로 수행 계획을 읽고, 인덱스 효과를 수치로 검증하는 방법을 배웠다

성능 수치(쿼리 수, 응답시간, 개선율)를 측정하고 기록하는 방법을 배웠다. 숫자가 있으면 설득력이 달라진다

기록을 자동화하면 나중에 문서화에 도움이 된다.

## 마치며

6명이 한 레포에서 65개 PR을 합치면서 큰 충돌 없이 마무리했다. 그 과정에서 N+1 제거, 인덱스 최적화, 커서 페이지네이션 같은 기술적인 결정들이 실제 수치로 돌아왔고, 그게 이 프로젝트에서 가장 만족스러운 부분이었다.

다음 프로젝트에서 챙길 것은 하나다. 성능을 마지막에 개선하는 게 아니라, 설계 단계에서 "이 구조가 나중에 문제가 될 수 있는가"를 먼저 질문하는 습관. 이번에 배운 것들을 다음에 쓸 때는 기술 부채로 남기지 않는다.

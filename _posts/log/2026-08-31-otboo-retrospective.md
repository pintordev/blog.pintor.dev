## 프로젝트 개요

날씨와 취향을 고려해 사용자가 보유한 의상 조합을 추천하고, OOTD 피드·팔로우·DM 같은 소셜 기능을 갖춘 개인화 의상 추천 SaaS **Otboo(옷장을 부탁해)** 를 4인 팀으로 개발했다. 기상청 단기예보를 수집해 추천에 쓰고, LLM으로 추천을 고도화하며, 피드 검색은 Elasticsearch로 처리한다.

스택은 Spring Boot 4.1 + PostgreSQL + Redis + Kafka + Elasticsearch. AWS ECS에 다중 인스턴스로 올리고 Nginx가 앞단에서 로드밸런싱한다. Spring Batch로 날씨 수집·데이터 정리·로그 백업·유실 이미지 정리 등 여러 Job을 운영하고, 실시간 통신은 알림에 SSE, DM에 WebSocket을 쓴다. [otboo.cc](https://otboo.cc)에 실서비스로 배포했다.

나는 팀장을 맡았고, 도메인으로는 **인프라·공통 + 날씨·알림** 을 담당했다. 프로젝트 초기화와 공통 예외 구조, CI/CD, 로컬·운영 분산 인프라, 커스텀 메트릭, 팀 자동화까지 인프라성 작업을 대부분 챙겼고, 팀원들 PR을 리뷰하며 개선 제안도 병행했다.

이번이 세 번째로 맡은 팀장이고, 여태 한 팀 중 가장 소규모였다.

## 내가 한 것들

### 날씨 조회 — 외부 API를 덜 부르게 만들기

프로젝트 초반의 `GET /api/weathers` 는 같은 좌표를 반복 조회해도 매 요청 기상청을 다시 불렀다. 원인은 파서에 있었다. "하루치 슬롯이 4개 미만이면 그날 데이터를 통째로 폐기"하는 조건 때문에, 늦게 도착한 예보의 잔여 슬롯이 버려지면서 "오늘 대표 슬롯"이 항상 낡은 값으로 남았고, stale 판정이 상시 참이 되어 매 요청 라이브 재조회로 이어졌다.

폐기 조건을 없애고 upsert 역행 방지 가드(오래된 값이 최신 값을 덮지 않게)를 넣은 뒤, 그 위에 캐싱을 얹었다.

- **Redis 캐시** — 격자 (x, y) 단위로 캐싱해 같은 격자를 공유하는 사용자끼리 결과를 공유
- **분산 single-flight** — 로컬 in-flight 맵 + Redis `SET NX` + Lua + Pub/Sub. 인스턴스가 여러 대여도 콜드미스가 겹치면 리더 1대만 기상청을 부르고 나머지는 캐시/신호로 결과를 받음
- **`DeferredResult` 전환** — 캐시 미스로 재조회를 기다리는 동안 Tomcat 요청 처리 스레드를 붙들지 않도록, 컨트롤러는 `DeferredResult`, 서비스는 전 구간 `CompletableFuture`

| 구분 | Before | After |
| --- | --- | --- |
| 같은 좌표 재조회 시 기상청 호출 | 매 요청 | 캐시 적중 시 0회, 미스 시 1회 |
| 인스턴스 2대 동시 콜드미스 | 2회 (각 인스턴스) | 1회 (리더만) |
| 캐시/외부 API 대기 중 Tomcat 워커 스레드 | 점유 | 비점유 |

같은 파서 버그가 매일 저녁 D0 급변 알림이 조용히 안 나가던 원인이기도 했다. D0 처리가 발표 정각 슬롯을 요구했는데 기상청은 발표 시각 +1h부터 슬롯을 주기 때문에 매칭이 0건이었다. 정각 요구를 버리고 가장 가까운 슬롯을 대표로 고르도록 재설계하니 알림이 정상 발행됐다.

### 알림 — 단일 인스턴스 전용에서 분산 전달로

초기 SSE 알림은 in-memory였다. 다른 인스턴스에서 발생한 알림은 전달되지 않았고, 이벤트 리스너가 원본 트랜잭션 안에서 DB 저장과 SSE 발행을 직접 해서 처리 중 인스턴스가 죽으면 유실, 재시도하면 중복이 생길 수 있는 구조였다. 이걸 네 단계에 걸쳐 분산 구조로 옮겼다.

1. **in-memory 재생 버퍼 정합성 정리** — 재연결 시 밀려난 emitter 미종료, 재생 종료조건 오판, evict된 id 재조회 시 전체 재전송 같은 버그 5건 수정. 짧은 연결 끊김은 최대 1,000건 재생 버퍼로 보완
2. **Redis Pub/Sub 전파** — 재생 버퍼를 Redis ZSet으로, 발행을 Pub/Sub 채널로 옮겨 전 인스턴스에 전파. 연결 시점 스냅샷 비교로 재생분과 실시간분의 중복 전송 차단
3. **Transactional Outbox + Kafka 릴레이** — 이벤트 발행 지점의 트랜잭션 안에서(`BEFORE_COMMIT`) outbox 행만 저장하고, ShedLock 스케줄러가 폴링해 Kafka로 발행. 인스턴스가 죽어도 outbox 행이 DB에 남아 자동 복구
4. **유실·중복·역압·순서 보완** — 큐 포화 시 조용한 유실을 `CallerRunsPolicy` 역압으로, 재생 순서를 `createdAt` → 단조 `seq` 로, 재시도 중복을 `UNIQUE(event_id, receiver_id)` 멱등 제약으로

네 개의 안전장치가 각각 다른 실패를 막는다.

| 실패 축 | 방어 |
| --- | --- |
| 발행 원자성 | Outbox 행 저장을 원본 트랜잭션에 결합 |
| 중복 실행 | 릴레이 스케줄러 `@SchedulerLock` 분산 락 |
| 중복 소비 | `UNIQUE(event_id, receiver_id)` 멱등 |
| 처리 실패 | 재시도 2회 + DLT (공용 `KafkaConfig`) |

2차 리뷰에서 "outbox 릴레이 동시 발행 시 중복 위험"을 다시 지적받았는데, 여기서는 별도 동시성 제어를 더하는 대신 `@SchedulerLock` 의 `lockAtMostFor` 가 최악 처리 시간보다 크기만 하면 인스턴스 간 중복이 구조적으로 불가능하다는 점을 근거로 배치 크기(100→20)·락 유지시간(1분→10분) 조정만으로 대응했다. 왜 대안(CAS 점유 방식)을 택하지 않았는지까지 리뷰 코멘트로 근거를 남겼다.

마지막으로 SSE 발행 성공/실패(`sse_delivered_at`)를 Kafka 컨슈머의 재시도 판단과 연결해, 알림 저장 신뢰성과 실시간 전달 신뢰성을 하나의 상태로 묶었다.

### 무중단 배포 중 장기 연결 유지 — Nginx 동적 upstream watcher

ECS 롤링 배포는 태스크 IP가 매번 바뀌는데 Nginx upstream은 기동 시점 값으로 고정된다. 그대로 두면 배포마다 SSE·WebSocket 장기 연결이 끊긴다.

Cloud Map을 15초 주기로 조회해 살아있는 인스턴스 IP 목록을 정렬 비교하고, 실제로 바뀌었을 때만 upstream 블록을 덮어쓰고 reload하는 watcher(systemd 타이머)를 붙였다. 정렬 없이 비교해 매번 reload되던 문제, `mv` 로 파일을 교체할 때 Nginx가 옛 inode를 계속 읽던 함정도 이 과정에서 잡았다.

### 관리자 메트릭 대시보드 — 순간값에서 시계열로

Actuator `/actuator/metrics` 는 순간값만 보여줘서 추이를 볼 수 없다. 이걸 CloudWatch 기반 시계열 조회로 확장했다.

- `CloudWatchEmfMeterRegistry` — Micrometer `StepMeterRegistry` 구현체로, 60초마다 화이트리스트를 통과한 메트릭만 CloudWatch EMF JSON을 로그로 찍는다. 앱이 CloudWatch API를 직접 부르지 않고 기존 stdout → CloudWatch Logs 파이프라인에 얹혀가는 방식이라 아웃바운드 호출이 늘지 않는다
- `MetricsDashboardService` 가 `getMetricData()` 로 시계열을 조회, 커스텀 Actuator `@Endpoint` 로 노출. 조회 범위는 1h/6h/12h/24h/7d/14d 프리셋 enum으로 제한
- otboo-fe 관리자 메뉴에 대시보드 화면(진입점, 범위 프리셋, 시계열 위젯)까지 직접 구현. 백엔드 API 설계와 화면을 같이 맡아 "차원(태그) 있는 메트릭은 이번 스코프에서 조회 불가"라는 제약까지 프론트와 맞췄다

이 밖에 배치 커스텀 메트릭(Job 성공/실패/소요시간, 스킵·정리 건수, 급변 알림 발행 건수), 배치 스케줄러 ShedLock 분산 락, 로그 백업 배치(CloudWatch Logs → S3), 유실 이미지 삭제 배치(S3 orphaned object cleanup)를 붙였다.

### 팀 인프라 — 시크릿 관리와 일정 자동화

팀 시크릿을 별도 private repo로 주고받는 스크립트가 `cp` 기반이라, `git pull` 로 최신을 받아와도 그 직후 로컬 파일로 통째로 덮어써 진짜 3-way 병합이 일어나지 않았다. 겹치지 않는 변경(서로 다른 키 추가)까지 사라질 위험이 있었다. 로컬 설정 파일을 시크릿 레포 클론 안 실제 파일을 가리키는 심볼릭 링크로 전환하니, 이후 흐름은 평범한 git 저장소와 똑같이 동작했다.

Notion 작업 트래커와 GitHub Issues/Projects를 매일 자동 동기화하고, 이슈·PR 필수 필드 누락을 자동 점검해 알리는 스크립트도 운영했다.

## 팀장으로서의 경험

Findex, MoNew에 이어 세 번째 팀장이었고, 4인으로 가장 작은 팀이었다. 소규모라 한 명의 공백이 전체 일정에 미치는 영향이 크다는 걸 초반부터 그라운드 룰에 못 박았다.

사전기간이 하루로 압축돼서, 07/24 오전에 공통 예외 구조·JWT 흐름·SSE 이벤트 인터페이스·커서 페이지네이션 같은 블로커성 결정을 ADR 스피드런으로 결론만 빠르게 내고, 오후에 각 담당자가 스켈레톤으로 반영했다. 이 순서 덕에 1차 스프린트가 시작될 때 후속 작업자가 패턴을 물어보는 대신 바로 코드를 짤 수 있었다.

세 번의 팀장 경험을 비교하면, 결국 팀 분위기는 시스템(컨벤션·문서·리뷰 프로세스)이 만드는 절반과 사람이 만드는 절반이 있다. 이번엔 4인 전원이 Fork 워크플로우, 2 approvals 룰, ADR 문서화를 프로젝트 끝까지 불만 없이 지켜줬다. 덕분에 팀 관리가 아니라 기술 결정과 공통 인프라에 시간을 쓸 수 있었고, 그게 이번 팀에서 가장 감사한 부분이다.

## 아쉬웠던 것들

**추정치 파라미터를 "안전"까지만 검증했다.** 배치 락 유지시간, outbox 릴레이 배치 크기, SSE 재생 버퍼 상한(1,000건)을 전부 실측 없이 보수적으로 잡았다. 성능 테스트에서 "이 값으로 목표 부하가 터지지 않는다"는 확인은 됐지만, "이게 적정값"이라는 근거는 아직 없다. 다행히 값은 전부 property로 빼둬서(`${batch.weather-fetch.lock-at-most-for:PT10M}`) 코드 변경 없이 조정 가능하고, Actuator 커스텀 메트릭·대시보드로 튜닝에 필요한 입력 데이터는 이미 모이고 있다. 남은 건 그 데이터를 값 조정으로 연결하는 것이다.

**분산 전환을 실패 축과 부딪히며 하나씩 메꿨다.** SSE 분산 전환이 처음이라 유실·중복·역압·순서를 처음부터 다 알고 시작한 게 아니라, 구현 → 멘토 리뷰 → 다음 PR 반영이라는 흐름을 타면서 한 주제가 여러 후속 PR로 이어졌다. 동작하는 구조엔 도달했지만, 축이 뒤늦게 드러날 때마다 이미 짜둔 코드를 되돌려 고쳤다. 다음 분산 전환은 착수 시점에 실패 축과 방어책을 설계 문서로 먼저 확정하고, 그 문서를 리뷰의 기준선으로 쓸 생각이다.

**크로스 인스턴스 검증이 수동이었다.** app-1/app-2 도달 확인을 매번 docker compose로 손으로 했고, 자동 통합 테스트로 최소 한 개라도 고정해두지 못했다.

## 배운 것들

분산에서 "발행(저장)"과 "전달(실시간)"은 별개의 신뢰성 문제고, 각각 따로 설계해야 한다. 마지막엔 SSE 발행 성공/실패를 Kafka 컨슈머 재시도 판단과 연결해 두 축을 하나의 상태로 묶었다.

원자성·멱등성·역압·순서는 한 번에 해결되지 않는다. Outbox+트랜잭션 결합, `UNIQUE(event_id, receiver_id)`, `CallerRunsPolicy`, 단조 `seq` — 네 개가 각자 다른 실패를 막는다.

`@SchedulerLock` 의 `lockAtMostFor` 가 최악 처리 시간보다 크기만 하면 인스턴스 간 중복 실행은 구조적으로 불가능하다. 이 근거가 있으면 불필요한 동시성 제어를 더 얹지 않아도 된다.

ECS 롤링 배포는 태스크 IP가 매번 바뀐다. 장기 연결을 유지하려면 Nginx가 서비스 디스커버리를 보고 upstream을 갱신해야 한다.

`cp` 기반 설정 동기화는 git이 있어도 3-way 병합을 못 한다. 심볼릭 링크로 "사본" 자체를 없애면 평범한 git 저장소가 된다.

## 마치며

4명이 한 레포에서 150개가 넘는 PR을 머지했고, 그중 55개가 내 PR이었다. 날씨·알림 양쪽에서 "단일 인스턴스 전제"를 걷어내 스케일아웃 가능한 구조로 만든 것, 그리고 메트릭 수집부터 관리자 대시보드 화면까지 관측 경로를 처음부터 끝까지 쌓은 게 이 프로젝트에서 가장 기억에 남는다.

다음 프로젝트에서 챙길 것은 두 가지다. 분산 전환은 실패 축과 방어책을 설계로 먼저 확정하고 시작하는 것. 그리고 추정치를 넣을 때 "어떤 메트릭을 언제 보고 어떤 값으로 좁힌다"를 후속 작업으로 같이 정의하는 것. 이번에 입력 데이터까지는 모아뒀으니, 다음엔 그걸 실제 튜닝으로 연결한다.
